**승인된 원칙**

1. 목표 포지션(Target Position), 실제 포지션(Filled Position), 예상 포지션(Projected Position)을 구분한다 (§5.1, R9-1).
2. 주문·체결 기록과 포지션 장부를 분리한다 (§6.1).
3. 실제 포지션은 검증된 기준 포지션과 중복 제거된 체결 기록으로 계산한다 (R9-2, R9-9).
4. 중복 주문을 막기 위해 진행 중 주문의 남은 수량을 반영한다 (R9-1).
5. 기대 예상 포지션과 위험 검사용 최악 경우 예상 포지션을 따로 계산한다 (§5.1, R9-7).
6. 주문 상태 11종과 상태 불명확(`UNKNOWN`)을 구분하는 구조를 채택한다 (§6.2).
7. `UNKNOWN`을 자동으로 거부·취소·실패로 보지 않는다 (R9-4).
8. `UNKNOWN`, Reconciliation 불일치, 체결 기록 충돌에서는 ACCEPTED ADR-0003의 `HALTED` 원칙을 따른다 (R9-8, R9-9, RP-3, RP-4, ADR-0003 §6.5).
9. `HALTED`를 자동으로 해제하지 않는다. 해제에는 원인 해소 확인, 대조 완료, 사용자 승인이 필요하다 (R9-12, ADR-0003 §6.5).
10. 취소 요청은 취소 확정과 다르다 (R9-6).
11. 롤의 각 다리를 별도 주문 상태로 관리한다 (R9-10).
12. 부분 체결은 개별 체결 기록으로 관리한다 (R9-3).
13. 체결 ID 기반 멱등성을 보장한다 (R9-9).
14. R1에서 정의한 체결 키의 고유성 범위(기본 키 계좌, 출처, 체결 ID)와 같은 키의 내용 충돌 검사 원칙을 채택한다 (§6.4a).
15. 정정(`REPLACE_REQUESTED`)에서 브로커의 원자성과 수량 의미가 불확실하면 보수적인 최악 경우 노출을 계산한다 (§6.2a RP-1).
16. 정정 전후 수량의 단순 `max` 규칙을 조건 없이 쓰지 않는다 (RP-2).
17. 정정 상태를 확인할 수 없으면 새로운 위험 증가 주문을 막고, 주문 상태가 `UNKNOWN`이면 `HALTED`로 처리한다 (RP-3, RP-5).
18. 백테스트의 즉시 전량 체결은 시뮬레이션 정책일 뿐 실제 주문 모델의 기본 가정이 아니다 (§6.1).
19. 기존 V1 경로는 바꾸지 않는다 (§6.1, §8).

## 4. Decision Drivers

1. **목표와 실제의 분리**: 목표 수량과 체결 수량을 혼동하지 않는다.
2. **검증된 기록에서 계산**: 실제 포지션은 검증된 체결 기록에서만 계산한다.
3. **멱등성**: 같은 체결 이벤트를 두 번 받아도 포지션과 현금이 한 번만 바뀐다.
4. **불명확함을 숨기지 않음**: 상태를 모르면 모른다고 기록하고, 자동 주문을 멈춘다 (ADR-0003).
5. **모드 간 공유**: 포지션 계산, 미체결 노출, 대조 계산은 Backtest/Paper/Live가 같은 순수 함수를 쓴다 (CLAUDE.md §4).
6. **구현 규모**: 하루 1회 점검 시스템에 맞는 복잡도.
7. **V1 호환**: V1 경로는 바꾸지 않는다.

## 5. Considered Options

### 5.1 개념 정의 (모든 대안에 공통)

| 개념 | 정의 |
|---|---|
| **Target Position** (목표 포지션) | 사이징·버퍼링·거래 전 위험 검사가 정한 원하는 수량. 주문이 아니다 |
| **Filled / Actual Position** (실제 포지션) | 기준 시점의 검증된 포지션 + 그 이후 반영된 체결 수량의 합. 거래 단위(월물 ID 또는 ETF 종목)별로 계산 |
| **Projected Position** (예상 포지션) | 실제 포지션 + 미체결 주문의 영향. 두 가지를 구분한다: (a) **기대 예상 포지션** = 실제 + 진행 중 주문의 남은 수량이 모두 체결된다고 볼 때 (중복 주문 방지용), (b) **최악 경우 예상 포지션** = ADR-0003 §6.3의 `q_long_worst`, `q_short_worst` (위험 검사용) |
| **Order Intent** (주문 의도) | 목표와 기대 예상 포지션의 차이에서 만든 주문 후보. 거래 전 위험 검사(ADR-0003 L2)와 L3 게이트를 통과하기 전에는 제출하지 않는다 |
| **Client Order ID** | 시스템이 주문 의도마다 만드는 고유 식별자. 재시도와 상태 조회에 같은 값을 쓴다. 브로커가 이를 중복 방지 키로 인정하는지는 D-12 |
| **Broker Order ID** | 브로커가 접수 후 부여하는 식별자. 접수 응답 전에는 없다 |
| **Fill** (체결) | 체결 ID, 주문 ID, 거래 단위, 수량(부호 있음), 체결가, 수수료와 수수료 통화, `fill_at`을 가진 기록. 부분 체결은 체결마다 하나의 기록 |
| **Filled Quantity / Remaining Quantity** | 체결된 수량의 합 / 주문 수량 − 체결 수량 − 취소 확정된 수량 |
| **Reconciliation** | 같은 기준 시각의 내부 포지션·미체결 주문·현금과 브로커 보고를 비교하는 일 (ADR-0003 S-3) |
| **Trading State** | 계좌 단위 `NORMAL` / `RESTRICTED` / `HALTED` (ADR-0003 §6.5) |

### 5.2 대안 A — 백테스트처럼 주문은 항상 전량 체결된다고 가정

- **내용**: V1처럼 주문 수량 = 체결 수량 = 새 포지션.
- **장점**: 단순하다. 연구 백테스트에는 충분할 수 있다 (예상 자본 규모에서 유동성 영향이 작을 것으로 보임, GAP F-08 INFERRED).
- **단점**: Paper/Live에 쓸 수 없다. 거부, 부분 체결, 상태 불명확을 표현할 수 없다. ADR-0003의 미체결 노출과 Reconciliation이 동작할 자리가 없다.

### 5.3 대안 B — 주문·체결 기록과 포지션 장부를 분리하고 체결 이벤트로 실제 포지션을 갱신

- **내용**: 주문(의도, 상태, 수량)과 체결(개별 기록)을 따로 두고, 실제 포지션은 체결 기록을 반영해서만 바꾼다. 체결 반영은 체결 ID로 멱등하게 한다.
- **장점**: 목표와 실제가 분리된다. 백테스트는 "즉시 전량 체결"을 **체결 시뮬레이션 정책**으로 쓰면서도 같은 기록 구조를 쓴다. Paper/Live 확장이 자연스럽다.
- **단점**: 주문 상태 전이를 관리해야 한다. 복구 시 어떤 기록을 신뢰할지 정해야 한다.

### 5.4 대안 C — 전체 Event Sourcing과 세부 주문 상태 기계

- **내용**: 모든 상태를 이벤트 로그에서 재구성하고, 브로커별 세부 상태까지 모델링한다.
- **장점**: 감사와 복구가 가장 강하다.
- **단점**: 구현과 유지 비용이 크다. 브로커가 정해지지 않은 지금 세부 상태를 정하면 맞지 않을 가능성이 크다 (D-12).

| 목표와 실제 구분 | 없음 | 있음 | 있음 |

| 멱등 체결 반영 | 해당 없음 | 체결 ID로 | 이벤트 ID로 |
| 공유 순수 계산 | 일부 (사이징, 비용) | 포지션 계산, 남은 수량, 최악 경우 노출, 대조 계산 | 같음 |
| 모드별 상태 관리 | 없음 | Paper/Live: 주문 상태 추적, 제출·취소·조회 (adapter) | 이벤트 저장소까지 |
| Backtest 적합성 | 높음 | 높음 (전량 체결을 정책으로) | 과함 |
| Paper/Live 적합성 | 부적합 | 적합 | 적합 |
| 복잡도 | 낮음 | 중간 | 높음 |
| V1 호환 | V1 그대로 | 새 경로 전용 | 새 경로 전용 |

## 6. Proposed Decision

### 6.1 결정 요지

**B를 채택한다.** 주문과 체결 기록을 포지션 장부와 분리하고, 실제 포지션은 검증된 체결 기록을 체결 ID 기준으로 한 번씩만 반영해 계산한다. Paper/Live에는 주문·체결 이벤트의 **추가 전용 기록**(append-only log)을 두어 감사와 복구에 쓰지만, 모든 상태를 이벤트로 재구성하는 C 전체는 채택하지 않는다.

- 백테스트의 "즉시 전량 체결"(A)은 **체결 시뮬레이션 정책**으로만 남는다. 백테스트도 체결 기록을 만들고 포지션은 그 기록에서 계산한다 (ADR-0005 E-8).
- V1 경로는 바꾸지 않는다.

### 6.2 주문 상태

| 상태 | 의미 | 종료 상태 | 최악 경우 노출에 남은 수량 포함 |
|---|---|---|---|
| `INTENT` | 만들어졌지만 제출 전 (위험 검사 전·후) | — | 아니오 (제출 전) |
| `PENDING_SUBMIT` | 제출 요청을 보냈고 응답을 기다림 | 아니오 | **예** |
| `ACCEPTED` | 브로커가 접수함 (Broker Order ID 있음), 체결 없음 | 아니오 | 예 |
| `REJECTED` | 브로커가 거부함 (체결 0) | 예 | 아니오 |
| `PARTIALLY_FILLED` | 일부 체결, 남은 수량 있음 | 아니오 | 예 (남은 수량) |
| `FILLED` | 전량 체결 | 예 | 아니오 |
| `CANCEL_REQUESTED` | 취소를 요청했고 확정을 기다림 | 아니오 | **예** (취소 확정 전) |
| `CANCELLED` | 취소 확정 (그 전까지의 체결은 유효) | 예 | 아니오 |
| `REPLACE_REQUESTED` | 정정을 요청했고 확정을 기다림 | 아니오 | 예. 기본은 **기존 남은 수량 + 새 수량(합)**. 큰 쪽(max)은 원자성과 수량 의미가 확인된 경우에만 (§6.2a, R1에서 변경) |
| `EXPIRED` | 유효기간 종료로 남은 수량 소멸 (브로커 확인) | 예 | 아니오 |
| `UNKNOWN` | 응답 유실, timeout 등으로 상태를 모름 | **아니오** | **예** (전량 체결된 것으로 간주, ADR-0003 §6.3) |

- 상태는 브로커 응답, 상태 조회, 체결 통보로만 바뀐다. 시스템이 요청을 보냈다는 사실만으로 결과 상태(`CANCELLED` 등)로 바꾸지 않는다.
- 브로커별 실제 상태 이름과 의미의 대응은 D-12에서 정한다.

### 6.2a 정정(Cancel/Replace) 중의 노출 계산 (R1)

정정은 브로커에 따라 (a) 기존 주문을 그 자리에서 바꾸는 **원자적 정정**일 수도 있고, (b) 기존 주문 취소와 새 주문 제출이 따로 처리되는 **비원자적 정정**일 수도 있다. 또 정정 수량이 (c) 체결분을 포함한 **누적 총수량**인지 (d) **새 남은 수량**인지도 브로커마다 다를 수 있다. 어느 쪽인지는 D-12에서 확인한다 (UNVERIFIED).

**R0의 "정정 전·후 중 큰 쪽(max)" 규칙의 반례**

| ID | 상황 | max 규칙의 최악 경우 | 실제 가능한 최대 | 결과 |
|---|---|---|---|---|
| CE-1 | 비원자적 정정. 기존 +5가 취소 확정 전에 전량 체결되고, 새 +8도 접수되어 전량 체결 | 0 + max(5, 8) = **8** | 5 + 8 = **13** | 과소평가 (위험) |
| CE-2 | 수량 의미 불일치. 기존 +5 중 3 체결 후 "+8로 정정". 시스템은 누적 총수량으로 보고 남은 수량을 5로 계산했지만, 브로커는 새 남은 수량 8로 처리 | 3 + max(2, 5) = **8**. 해석한 값으로 합을 내도 3 + 2 + 5 = 10 | 3 + 8 = **11** (비원자적이면 3 + 2 + 8 = 13) | 과소평가 (위험). RP-1의 보수적 해석(요청 수량 8을 새 남은 수량으로)으로 3 + 2 + 8 = **13** ≥ 11 |
| CE-3 | 체결 통보와 정정 확정의 순서 역전. 정정 확정을 먼저 받고 그 뒤 기존 주문의 체결 통보가 도착 | 정정 확정 시점의 체결 수량으로 남은 수량을 계산했다면 늦은 체결만큼 틀림 | 늦은 체결 수량에 따라 다름 | 체결을 주문 ID로 귀속하고 남은 수량을 다시 계산해야 함 |
| CE-4 | 정정 거부. 기존 주문이 그대로 유효 | 기존 남은 수량 | 기존 남은 수량 | max 규칙도 안전 |

**규칙 (R1)**

| ID | 규칙 |
|---|---|
| RP-1 | `REPLACE_REQUESTED` 동안 최악 경우 노출의 기본값은 **기존 주문의 남은 수량 + 새 주문 수량(합)**이다. 여기서 "새 주문 수량"은 가장 보수적인 해석, 즉 **요청한 정정 수량 전체를 새 남은 수량으로** 본다 (누적 총수량으로 해석해 체결분을 빼지 않는다, CE-2). ADR-0003 §6.3이 미체결 매수 주문들을 합하는 것과 같은 방향이다 |
| RP-2 | max 규칙은 다음이 **모두 확인된 경우에만** 쓸 수 있다: 브로커가 원자적 정정을 보장함, 정정 수량의 의미(누적 / 남은)를 알고 시스템이 같은 의미로 계산함, 정정 전후의 체결이 같은 주문 체인으로 귀속됨 |
| RP-3 | 상태가 알려진 `REPLACE_REQUESTED`이지만 브로커의 정정 원자성이나 정정 결과가 아직 확인되지 않았으면, 그 상품의 **자동 위험 증가 주문을 허용하지 않는다.** 수량을 늘리는 정정도 위험 증가 주문이다. 주문 상태 자체를 알 수 없게 되면(`UNKNOWN`) 상품 단위 차단이 아니라 계좌 단위 `HALTED`다 (RP-4, RP-5, ADR-0003 §6.5) |
| RP-4 | 정정·취소 확정과 체결 통보의 순서가 불명확하면, 체결은 체결 기록의 주문 ID로 귀속하고 각 주문의 남은 수량을 다시 계산한다. 귀속할 주문 ID가 없거나 계산이 서로 맞지 않으면 `UNKNOWN`으로 두고 `HALTED`로 바꾼다 |
| RP-5 | 정정 응답이 timeout이면 기존·새 주문 모두 `UNKNOWN`이다. 재정정이나 재제출을 하지 않는다 (R9-5) |

### 6.3 규칙

| ID | 규칙 | 근거 |
|---|---|---|
| R9-1 | 목표 수량과 체결 수량을 다른 필드, 다른 기록에 둔다. 새 주문 의도 = 목표 − **기대 예상 포지션** (실제 + 진행 중 주문의 남은 수량). 진행 중 주문이 있는데 목표 − 실제로 다시 주문하지 않는다 | 요구 1 |
| R9-2 | 실제 포지션 = 기준 포지션(검증된 시점) + 반영된 체결의 합. 목표나 주문 수량에서 포지션을 만들지 않는다 | 요구 2, ADR-0005 E-8 |
| R9-3 | 부분 체결마다 체결 ID, 수량, 체결가, 수수료와 수수료 통화, `fill_at`을 기록한다. 평균 체결가는 계산 결과일 뿐 원본 기록이 아니다 | 요구 3, ADR-0001 체결분 항 |
| R9-4 | `UNKNOWN`을 `REJECTED`, `CANCELLED`, 실패로 바꾸지 않는다. 상태 조회나 체결 통보로 확인될 때까지 `UNKNOWN`이다 | 요구 4 |
| R9-5 | timeout 뒤 같은 주문을 자동으로 다시 제출하지 않는다. 같은 Client Order ID로 상태를 조회한다. 조회할 수 없으면 기다리고 사람에게 알린다 | 요구 5, ADR-0003 §6.3, §6.5 |
| R9-6 | 취소 요청만으로 취소되었다고 보지 않는다. `CANCEL_REQUESTED` 동안 들어온 체결은 반영하고, 남은 수량은 최악 경우 노출에 계속 넣는다 | 요구 6 |
| R9-7 | 최악 경우 예상 포지션은 ADR-0003 §6.3 식을 쓴다. `PENDING_SUBMIT`, `ACCEPTED`, `PARTIALLY_FILLED`, `CANCEL_REQUESTED`, `REPLACE_REQUESTED`, `UNKNOWN`의 남은 수량을 넣는다. 미체결 위험 축소 주문은 노출을 줄이는 쪽으로 반영하지 않는다 | 요구 7 |
| R9-8 | 브로커와 내부의 포지션·미체결·현금이 같은 기준 시각에서 다르면 Trading State를 `HALTED`로 바꾸고 자동 주문을 막는다 | 요구 8, ADR-0003 S-3 |
| R9-9 | 체결 반영은 멱등 키 (계좌, 출처, 체결 ID)로 멱등하다 (§6.4a). 같은 키가 다시 오면 §6.4a의 모든 필드를 비교한다. 모두 같으면 포지션과 현금을 바꾸지 않는다. 하나라도 다르면(수량, 가격, 월물뿐 아니라 `fill_at`, 수수료 금액·통화, 주문 ID 포함) 데이터 무결성 오류로 `HALTED`. 복구 때 브로커 체결 내역을 다시 읽어도 같은 규칙으로 중복 반영을 막는다 | 요구 9 |
| R9-10 | 선물 롤의 두 다리는 같은 그룹 ID로 묶되 각 다리는 자기 상태를 가진다. 그룹 상태(`COMPLETE`, `PARTIAL`, `NOT_STARTED`)는 다리 상태에서 계산한다. 한 다리만 체결된 상태를 정상적으로 표현한다 | 요구 10, ADR-0006 |
| R9-11 | ETF 체결은 현금 이벤트(체결 대금, 수수료, 결제 예정일, 결제 상태)를 함께 만든다. 결제 상태 전이는 ADR-0008 §6.6의 원장에 기록한다 | 요구 11, ADR-0008 |
| R9-12 | `HALTED`에서는 자동 주문(위험 축소 포함)을 만들지도 제출하지도 않는다. 수동 복구는 별도 절차와 승인 | 요구 12, ADR-0003 §6.5 |
| R9-13 | 체결의 평가 주기 귀속은 `fill_at`과 `valuation_at`으로 정한다. 주기 종료 시점의 실제 포지션에는 그 시각까지의 체결만 들어간다. 브로커 포지션과 비교할 때는 같은 기준 시각으로 맞춘다 | ADR-0001 §5.1.3 |

### 6.4a 체결 ID의 멱등 범위와 동일성 검사 (R1)

**멱등 키의 범위**

| 범위 | 판단 |
|---|---|
| 계좌 | 다른 계좌의 체결 ID와 겹칠 수 있다. 키에 계좌를 포함한다 |
| 브로커(체결 정보 출처) | 다른 브로커·시뮬레이터의 ID와 겹칠 수 있다. 키에 출처를 포함한다 |
| 주문 | 브로커가 체결 ID를 주문 안에서만 고유하게 보장한다면 키에 Broker Order ID를 포함해야 한다. 브로커가 날짜별로 ID를 다시 쓰는지도 확인해야 한다 (D-12, UNVERIFIED) |

- 기본 키: **(계좌, 체결 정보 출처, 체결 ID)**. 브로커의 고유성 보장 범위가 이보다 좁으면 D-12에서 키를 넓힌다 (예: Broker Order ID, 거래일 추가). 확인 전에는 그 브로커를 Live에 쓰지 않는다 (§6.4).

**동일성 검사 대상 필드**

같은 키로 체결 기록이 다시 오면 다음 필드를 모두 비교한다.

| 필드 | 비교 |
|---|---|
| Client Order ID, Broker Order ID | 같아야 함 |
| 거래 단위 (월물 ID / ETF 종목) | 같아야 함 |
| 방향과 부호 있는 수량 | 같아야 함 |
| 체결가 | 같아야 함 (부동소수점이 아닌 원본 값 기준. 표현 규칙은 P0-03) |
| `fill_at` | 같아야 함 |
| 수수료 금액과 수수료 통화 | 같아야 함 |
| (브로커가 주는 경우) 체결 시장, 유동성 구분 | 같아야 함 |

- **모든 필드가 같으면** 중복 수신이다. 포지션과 현금을 바꾸지 않고 중복 수신만 기록한다.
- **하나라도 다르면** 데이터 무결성 오류다. 두 번째 기록을 반영하지 않고, 두 기록을 모두 보관하며, Trading State를 `HALTED`로 바꾼다. "수량과 가격이 같으니 중복"으로 처리하지 않는다 (AT-0009-10).
- 브로커가 체결을 정정하거나 취소(체결 취소)하는 경우는 같은 ID의 재전송이 아니라 **명시적인 정정 이벤트**로 받아야 한다. 정정 이벤트의 형식과 처리는 D-12 (Q9-11).

### 6.5 공유 계산과 모드별 책임

| 계산 / 책임 | Backtest | Paper | Live |
|---|---|---|---|
| 실제 포지션 = 기준 + 체결 합 (멱등) | 공유 순수 함수 | 같음 | 같음 |
| 남은 수량, 기대·최악 경우 예상 포지션 | 공유 | 같음 | 같음 |
| 주문 의도 = 목표 − 기대 예상 포지션 | 공유 | 같음 | 같음 |
| Reconciliation 차이 계산 | 내부 = 기준이므로 항상 일치 | 시뮬레이터 상태와 비교 | 브로커 보고와 비교 |
| 체결 생성 | 시뮬레이션 정책 (즉시 전량 체결 등) | 시뮬레이터 (부분 체결·거부도 가능하게) | 브로커 체결 통보 |
| 주문 상태 추적, 제출·취소·조회, timeout | 해당 없음 | adapter (가짜 브로커) | adapter (D-12) |
| Trading State 전이 (L3) | 해당 없음 (V1 호환은 사후 검사) | 적용 | 적용 |

## 7. Consequences / Trade-offs

**장점**
- 목표, 실제, 예상 포지션이 분리되어 부분 체결과 미체결을 정확히 표현한다.
- 같은 체결이 두 번 와도 장부가 틀어지지 않는다.
- ADR-0003의 미체결 노출, 안전 조건, HALTED가 실제로 동작할 구조가 생긴다.
- 백테스트와 Paper/Live가 같은 포지션 계산을 쓴다.

**단점과 비용**
- 주문 상태 전이와 timeout 처리를 구현하고 테스트해야 한다.
- `UNKNOWN`과 불일치가 생기면 사람이 개입할 때까지 자동 거래가 멈춘다. 하루 1회 점검 운영에서는 멈춘 상태가 길어질 수 있다 (의도한 비용).
- 브로커가 체결 ID나 멱등 키를 지원하지 않으면 추가 설계가 필요하다 (D-12).

## 8. Compatibility with V1

이 ADR은 ADR-0001 §8.0(세 ADR 공통)의 `V1_COMPAT` 적용 범위를 그대로 따른다.

| 항목 | 영향 |
|---|---|
| V1 경로 | 변경 없음. 새 포지션 = 목표, 전량 체결 |
| 기존 306개 테스트, fingerprint | 변경 없음 |
| V1 재현 (`V1_COMPAT`) | 새 엔진은 "즉시 전량 체결" 시뮬레이션 정책으로 체결 기록을 만들고, 그 기록에서 포지션을 계산한다. 전량 체결이므로 결과 포지션은 V1과 같아야 한다 (ADR-0005 AT-0005-3에서 확인) |
| 새 경로 | 주문·체결 기록을 쓴다. 부분 체결 시뮬레이션 여부는 Q9-7 |

## 9. Financial Integrity Implications

- **이중 주문**: 진행 중 주문을 무시하고 목표 − 실제로 다시 주문하면 목표보다 많이 산다 (AT-0009-1: 5계약 목표에 최대 8계약).
- **이중 체결 반영**: 같은 체결을 두 번 반영하면 포지션과 현금이 실제보다 커진다 (AT-0009-4).
- **불명확 상태의 오처리**: `UNKNOWN`을 실패로 보고 재주문하면 실제로는 두 배를 보유할 수 있다 (AT-0009-2).
- **취소 오판**: 취소 요청만으로 취소로 보면 그사이 체결을 놓친다 (AT-0009-3).
- **롤 중간 상태**: 한 다리만 체결되면 노출이 목표와 다르다. 신월물을 먼저 사면 일시적으로 두 배 노출, 구월물을 먼저 팔면 일시적으로 0 노출이 된다. 순서는 정하지 않았다 (Q9-3).
- **주기 귀속**: 평가 시각 이후 체결을 그 주기에 넣으면 주기 손익과 위험 snapshot이 틀어진다 (ADR-0001 AT-0001-7, AT-0009-7).

## 10. Acceptance Criteria

인수 테스트는 **명세**다. 이번 작업에서 구현하지 않았다. 상품은 가상의 선물 월물 `F1-A`(구월물), `F1-B`(신월물)와 가상의 ETF `E1`이다. 가격과 수수료는 기록 형식을 보이기 위한 숫자다.

각 테스트의 기대 결과는 **실제 포지션 / 남은(미체결) 수량 / 주문 상태 / Trading State / 자동 주문 허용 여부**를 적는다.

### AT-0009-1 목표 +5계약, 주문 +5계약, 실제 +2계약만 부분 체결 (시나리오 A)

- **입력**: 실제 0. 목표 +5. 주문 O1(Client ID `C-001`) +5 → `ACCEPTED`. 체결 `X-1` +2 @ 100.10, 수수료와 시각 기록
- **기대 결과**:

| 실제 포지션 | 남은 수량 | 주문 상태 | Trading State | 자동 주문 |
|---|---|---|---|---|
| **+2** | **+3** | `PARTIALLY_FILLED` | `NORMAL` | 허용. 단 다음 의사결정의 새 주문 의도 = 5 − (2 + 3) = **0** |

  - 최악 경우 롱 포지션 = 2 + 3 = 5 (ADR-0003 §6.3)
  - 잘못된 처리: 목표 − 실제 = +3을 새로 주문하면 기존 남은 3과 합쳐 최대 8계약 보유 가능
- **전제조건**: R9-1, R9-2, R9-7
- **예외조건**: 체결 수량이 주문 수량을 넘으면(누적 > 5) 데이터 무결성 오류로 `HALTED`
- **V1 호환성 영향**: 없음 (V1은 부분 체결이 없음)
- **새 테스트 후보**: `test_partial_fill_keeps_target_and_actual_separate`, `test_no_duplicate_order_while_remaining_quantity_open`

### AT-0009-2 timeout 뒤 늦게 체결 통보가 도착 (시나리오 B)

- **입력**: 실제 0. 주문 `C-002` +5 제출 → 응답 timeout. 이후 브로커가 체결 `X-2` +5를 통보 (`fill_at`은 평가 시각 이전)
- **기대 결과**:

| 시점 | 실제 포지션 | 남은 수량 | 주문 상태 | Trading State | 자동 주문 |
|---|---|---|---|---|---|
| timeout 직후 | 0 | +5 (전량 체결로 간주해 최악 경우에 포함) | `UNKNOWN` | **`HALTED`** | **금지**. 재제출 없음, `C-002`로 상태 조회 |
| 체결 통보 후 | **+5** (한 번 반영) | 0 | 상태 조회로 확인되면 `FILLED` | **`HALTED` 유지** | **금지**. 원인 해소 확인 + Reconciliation + 사용자 승인 후 해제 (ADR-0003 §6.5) |

- **전제조건**: R9-4, R9-5, R9-12
- **예외조건**: 상태 조회도 실패하면 `UNKNOWN`과 `HALTED`를 유지하고 사람에게 알림. 체결 `fill_at`이 평가 시각 이후면 다음 주기에 귀속 (AT-0009-7)
- **V1 호환성 영향**: 없음
- **새 테스트 후보**: `test_timeout_sets_unknown_and_halts_without_resubmission`, `test_late_fill_applied_once_after_unknown`

### AT-0009-3 취소 요청 중 추가 체결 (시나리오 C)

- **입력**: 주문 `C-003` +5, 체결 +2 후 취소 요청. 취소 확정 전에 체결 `X-4` +1. 그 뒤 브로커가 취소 확정
- **기대 결과**:

| 시점 | 실제 포지션 | 남은 수량 | 주문 상태 | Trading State | 자동 주문 |
|---|---|---|---|---|---|
| 취소 요청 직후 | +2 | +3 | `CANCEL_REQUESTED` | `NORMAL` | 허용. 단 남은 3을 노출에 포함하고 같은 상품에 새 주문을 만들지 않음 |
| 추가 체결 후 | **+3** | +2 | `CANCEL_REQUESTED` | `NORMAL` | 같음 |
| 취소 확정 후 | +3 | **0** | `CANCELLED` (체결 3) | `NORMAL` | 허용. 새 주문 의도 = 목표 − 3 |

- **전제조건**: R9-6
- **예외조건**: 취소 응답이 오지 않고 timeout이면 `UNKNOWN`, `HALTED`
- **새 테스트 후보**: `test_cancel_request_is_not_cancellation`, `test_fill_during_cancel_pending_is_applied`

### AT-0009-4 같은 체결 이벤트를 두 번 수신 (시나리오 D)

- **입력**: 체결 `X-5` (+2 @ 100.10, 수수료 2.0 USD)를 두 번 받음. 복구 중 브로커 체결 내역에서 `X-5`를 한 번 더 읽음
- **기대 결과**:

| 실제 포지션 | 현금 변화 | 주문 상태 | Trading State | 자동 주문 |
|---|---|---|---|---|
| **+2** (+4 아님) | 한 번만 반영 | 변화 없음 | `NORMAL` (중복 수신만 기록) | 허용 |

  - 변형: 같은 `X-5`인데 수량이 +3으로 다르게 옴 → 데이터 무결성 오류, **`HALTED`**, 자동 주문 금지
- **전제조건**: R9-9
- **새 테스트 후보**: `test_duplicate_fill_id_is_idempotent`, `test_conflicting_fill_with_same_id_halts`

### AT-0009-5 내부 +3계약, 브로커 +2계약 불일치 (시나리오 E)

- **입력**: 같은 기준 시각에서 내부 실제 포지션 +3, 브로커 보고 +2. 목표 0
- **기대 결과**:

| 실제 포지션 (내부 / 브로커) | 남은 수량 | 주문 상태 | Trading State | 자동 주문 |
|---|---|---|---|---|
| +3 / +2 (불일치 기록) | 0 | — | **`HALTED`** (사유 `RECONCILIATION_MISMATCH`) | **금지** (위험 축소 주문 −3도 내지 않음) |

  - 내부 기준으로 −3을 내면 브로커 포지션은 −1이 되어 새 매도 노출이 생긴다 (ADR-0003 AT-0003-8과 같음)
- **전제조건**: R9-8, 같은 기준 시각 비교 (R9-13)
- **예외조건**: 브로커 조회 실패는 일치로 보지 않음 → `HALTED`
- **새 테스트 후보**: `test_reconciliation_mismatch_halts_auto_orders`

### AT-0009-6 선물 롤: 구월물 매도 체결, 신월물 매수 미체결 (시나리오 F)

- **입력**: 실제 `F1-A` +5. 목표: 롤 후 `F1-B` +5. 그룹 `G-1`: 다리 1 `F1-A` −5, 다리 2 `F1-B` +5. 다리 1 `FILLED`, 다리 2 `ACCEPTED`(체결 0)
- **기대 결과**:

| 거래 단위 | 실제 포지션 | 남은 수량 | 주문 상태 |
|---|---|---|---|
| `F1-A` | **0** | 0 | `FILLED` |
| `F1-B` | **0** | **+5** | `ACCEPTED` |
| 그룹 `G-1` | 상품 순노출 0 (목표 +5) | — | `PARTIAL` |

  - Trading State `NORMAL` (상태는 모두 알려져 있음). 자동 주문: 다리 2가 진행 중이므로 같은 다리를 다시 내지 않음. 최악 경우 롱 = +5
  - 다리 2가 `UNKNOWN`이 되면 `HALTED`, 자동 주문 금지
  - 다리 2가 세션 종료로 `EXPIRED`가 되면 그룹은 `PARTIAL`로 남고 다음 의사결정에서 다시 판단 (방식은 Q9-3)
- **전제조건**: R9-10
- **예외조건**: 다리 순서(신월물 먼저 / 구월물 먼저 / 동시)는 정하지 않음. 신월물이 먼저 체결되면 일시적으로 +10 노출이 되며, ADR-0003 S-4와 최악 경우 검사가 이를 다뤄야 함
- **V1 호환성 영향**: 없음 (V1은 두 다리를 원자적으로 체결)
- **새 테스트 후보**: `test_roll_group_tracks_leg_states_independently`, `test_no_resubmission_of_working_roll_leg`

### AT-0009-7 평가 시각 이후 체결이 다음 평가 주기에 귀속 (시나리오 G)

- **입력**: 주문 +5 `ACCEPTED`. 체결 `X-7` +5의 `fill_at`이 `valuation_at(t)` 이후 (가격은 ADR-0001 AT-0001-7과 같고 수량만 5계약: 체결가 104.1, `V[t]` 104, `V[t+1]` 105, M = 10, 수수료 10)
- **기대 결과**:

| 시점 | 실제 포지션 | 남은 수량 | 주문 상태 | Trading State | 자동 주문 |
|---|---|---|---|---|---|
| 주기 t 종료 기준 | **0** | +5 | `ACCEPTED` | `NORMAL` | 허용 (남은 수량 고려) |
| 체결 후 | +5 | 0 | `FILLED` | `NORMAL` | 허용 |

  - 회계: 주기 t 손익 0, 주기 t+1 체결분 손익 5 × (105 − 104.1) × 10 − 10 = 35 (ADR-0001 §5.1.3)
  - 브로커 포지션 스냅샷이 체결 이후 시각에 찍혔다면 +5다. 주기 t 종료 기준 내부 포지션 0과 비교하지 않고 같은 시각으로 맞춰 비교한다 (거짓 불일치 방지)
- **전제조건**: R9-13
- **새 테스트 후보**: `test_post_valuation_fill_goes_to_next_period`, `test_reconciliation_aligns_reference_time`

### AT-0009-8 ETF 매수 체결의 현금과 결제 상태

- **입력**: ETF `E1` 100주 매수 체결 @ 10.02 USD, 수수료 1.00 USD. 결제일은 가상 T+2 (실제 규칙은 UNVERIFIED)
- **기대 결과**:

| 실제 포지션 | 남은 수량 | 주문 상태 | 현금 | Trading State | 자동 주문 |
|---|---|---|---|---|---|
| +100주 (체결 즉시) | 0 | `FILLED` | 미결제 지급 1,003.00 USD (가상 T+2에 결제 완료). 사용 가능 현금은 체결 시 감소 | `NORMAL` | 허용 |

  - NAV 영향은 ADR-0008 AT-0008-3 (체결분 −2.00 + 수수료 −1.00 USD)
- **전제조건**: R9-11, ADR-0008 §6.6
- **새 테스트 후보**: `test_etf_fill_creates_unsettled_cash_event`

### AT-0009-9 정정 중 기존 +5와 새 +8이 동시에 유효할 수 있는 경우 (R1 추가)

- **입력**: 실제 포지션 0. 기존 매수 주문 `C-009` +5 `ACCEPTED` (체결 0). 이 주문을 +8로 바꾸는 정정 요청이 제출되어 `REPLACE_REQUESTED`. 브로커의 정정 원자성과 수량 의미는 확인되지 않음 (D-12)
- **기대 결과**:

| 시점 | 실제 포지션 | 최악 경우 롱 노출 | 주문 상태 | Trading State | 자동 주문 |
|---|---|---|---|---|---|
| 정정 요청 직후 | 0 | 0 + 5 + 8 = **13** (합, RP-1). max(5, 8) = 8로 계산하지 않음 | 기존 `REPLACE_REQUESTED`, 새 주문 제출됨 | `NORMAL` (상태 응답을 받는 중) | 그 상품의 **위험 증가 주문 차단** (RP-3). 추가 정정도 하지 않음 |
| 정정 응답 timeout | 0 | 13 유지 | 기존·새 주문 모두 `UNKNOWN` | **`HALTED`** | **금지** (재정정·재제출 없음) |
| 브로커가 원자적 정정 확정 (기존 취소, 체결 0, 새 +8 유효) | 0 | 8 | 기존 `CANCELLED`(또는 정정됨), 새 `ACCEPTED` | `HALTED`였다면 원인 해소 확인 + 대조 완료 + 사용자 승인 전까지 유지 | `NORMAL`로 돌아온 뒤에만 허용 |

  - max 규칙이 위험한 이유: 비원자적 정정이면 기존 +5와 새 +8이 모두 체결되어 13계약이 될 수 있다 (CE-1)
- **전제조건**: §6.2a, ADR-0003 §6.3
- **예외조건**: 정정 체결이 어느 주문의 것인지 알 수 없으면 `UNKNOWN`, `HALTED` (RP-4)
- **V1 호환성 영향**: 없음 (V1에는 정정이 없음)
- **새 테스트 후보**: `test_replace_pending_uses_sum_of_old_and_new_quantities`, `test_unconfirmed_replace_blocks_risk_increase`, `test_replace_timeout_halts`

### AT-0009-10 같은 체결 ID로 체결 시각이나 수수료 통화가 다르게 재수신 (R1 추가)

- **입력**: 체결 키 (계좌 `A1`, 출처 `BRK`, 체결 ID `X-10`)로 첫 기록: +2 @ 100.10, `fill_at` 10:01:05, 수수료 2.00 USD. 반영 후 같은 키로 두 번째 기록이 옴: (a) 수량·가격·수수료는 같고 `fill_at`만 10:01:07, (b) 수량·가격·시각은 같고 수수료 통화만 KRW
- **기대 결과**:

| 경우 | 실제 포지션 | 현금 | 판정 | Trading State | 자동 주문 |
|---|---|---|---|---|---|
| 모든 필드가 같은 재수신 (비교 기준) | +2 | 변화 없음 | 중복 수신 기록 | `NORMAL` | 허용 |
| (a) `fill_at`만 다름 | **+2** (두 번째 미반영) | 변화 없음 | **데이터 무결성 오류**. 두 기록 모두 보관 | **`HALTED`** | **금지** |
| (b) 수수료 통화만 다름 | **+2** (두 번째 미반영) | 변화 없음 | **데이터 무결성 오류** | **`HALTED`** | **금지** |

  - (a), (b)를 "수량과 가격이 같으니 중복"으로 무시하지 않는다. `fill_at`은 평가 주기 귀속(ADR-0001 §5.1.3)을, 수수료 통화는 현금 원장(ADR-0008 F8-1)을 바꾸기 때문이다
- **전제조건**: §6.4a, R9-9
- **예외조건**: 브로커의 체결 정정은 명시적 정정 이벤트로만 받는다 (Q9-11). 정정 이벤트 형식이 정해지기 전에는 이런 경우를 자동으로 처리하지 않는다
- **새 테스트 후보**: `test_same_fill_id_with_different_fill_time_halts`, `test_same_fill_id_with_different_fee_currency_halts`
