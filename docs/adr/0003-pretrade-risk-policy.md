### 3.2 문제

- CLAUDE.md §8은 "위험 한도를 위반하면 신규 주문을 차단한다"고 요구한다. V1은 주문을 차단하지 않고 사후에 실패한다.
- 사후 검사의 기준(종가 계좌, 당일 quote)은 주문 시점에 알 수 없는 정보다. 백테스트의 일관성 검사로는 쓸 수 있지만, 주문 판단 기준으로 옮기면 look-ahead가 된다 (INFERRED).
- V1은 미체결 주문 개념이 없다. 새 포지션 = 목표 포지션(전량 체결 가정)이다 (`contract_aware_daily_step.py:266`).

## 4. Decision Drivers

1. **제한된 손실 허용**: 한도를 넘는 위험을 미리 막는다.
2. **검증된 위험 축소는 막지 않음**: 한도를 넘은 상태에서 포지션을 줄이는 주문까지 막으면 위험이 더 커진다. 다만 "줄이는 주문"이라는 분류 자체가 틀릴 수 있다(내부 포지션 오류, 미체결 주문, 다른 한도 악화). 그래서 축소 주문에도 안전 조건을 둔다 (R1, §6.2.1).
3. **시점 무결성**: 주문 판단에는 주문 시점에 알 수 있는 계좌와 가격만 쓴다.
4. **모드 간 공유**: 위험 *계산*은 Backtest/Paper/Live가 같은 순수 함수를 쓴다 (CLAUDE.md §4).
5. **결정론과 감사 가능성**: 같은 입력이면 같은 결정이 나오고, 거부·축소 사유가 기록되어야 한다.
6. **V1 호환성**: 기존 가드레일 테스트를 보존할 수 있어야 한다.

## 5. Considered Options

### 5.1 대안 A — 기존 사후 검사 유지

- 내용: 거래 후 검사하고 위반하면 중단한다.
- 장점: 변경이 없다. 백테스트 설정 오류를 바로 알려 준다.
- 단점: 주문을 막지 못한다. Live에는 쓸 수 없다. 백테스트 하나가 위반 하루 때문에 통째로 실패하므로 연구에 불편하다.

### 5.2 대안 B — 주문 전 예상 위험 검사, 위반 시 위험 증가 주문 거부

- 내용: 주문 후 예상 포지션(미체결 포함)으로 위험을 계산한다. 한도를 넘으면 **위험을 늘리는 주문을 거부**하고 현재 포지션을 유지한다.
- 장점: 단순하고 보수적이다. 결정이 이진적이라 설명하기 쉽다.
- 단점: 목표가 한도를 조금만 넘어도 증가분 전체를 거부하므로 목표 추종이 덜 된다. 증가분의 일부는 한도 안에 들어갈 수 있는데도 거부된다.

### 5.3 대안 C — 한도를 넘는 목표를 허용 범위로 축소한 뒤 주문

- 내용: 한도를 만족하는 최대 수량으로 목표를 줄인다. 이때 반올림은 0 쪽(toward zero)으로 한다.
- 장점: 한도 안에서 목표에 가장 가깝게 따라간다.
- 단점: 새로운 포지션 계산 규칙이 생긴다. 금융 공식 추가에 해당하므로 명세와 독립 검증이 필요하다. 여러 한도와 여러 상품이 걸려 있으면 축소량을 어떻게 배분할지 정해야 한다. 원래 목표의 반올림 규칙(`round_half_away_from_zero`)과 다른 규칙이 섞인다.

## 6. Proposed Decision

### 6.1 결정 요지

**B를 기본 정책으로 제안한다. 위험을 늘리는 주문은 한도를 위반하면 거부한다. 위험을 줄이는 주문은 안전 조건(§6.2.1)과 포트폴리오 전체 검사(§6.2.2)를 통과한 경우에만 "검증된 위험 축소 주문"으로 보고, 한도 위반 상태에서도 정책상 허용할 수 있다. 조건을 충족하지 못하면 자동 주문을 차단한다. C(한도까지 축소)는 명시적으로 켜는 선택 모드로 두고, 기본값으로 할지는 P0-04의 수치 검증 후 사용자가 결정한다. A(사후 검사)는 V1 호환 모드에서 일관성 검사로만 유지한다.**

R0의 "위험을 줄이는 주문은 한도 위반 상태에서도 허용한다"(무조건 허용)는 R1에서 철회한다.

구조는 세 층이다.

| 층 | 내용 | 성격 |
|---|---|---|
| L1 위험 계산 | 예상 포지션, 노출, leverage, margin, 단일 상품 노출, 현금 요구량, drawdown, 신선도 판정 | 순수 함수. 세 모드 공유 |
| L2 정책 결정 | 주문 후보별로 `ALLOW` / `REDUCE_TO_LIMIT`(C 모드) / `BLOCK_INCREASE`와 사유 코드 결정 | 순수 함수. 세 모드 공유 |
| L3 상태 게이트 | 거래 상태 `NORMAL` / `RESTRICTED` / `HALTED` 결정 (브로커 대조, 주문 상태, 데이터 수신) | Paper/Live 전용 (Imperative Shell) |

**처리 순서**: 목표 포지션 (V1 사이징) → 버퍼링 → 거래 허용 판단 (ADR-0002) → **L2 정책** → L3 게이트 → 주문

### 6.2 위험 증가와 위험 축소의 분류

- 주문 후보 하나를 기준으로, `|q_after| ≤ |q_before|`이고 부호가 바뀌지 않으면 **위험 축소**다.
- 부호가 바뀌는 반전 주문은 두 다리로 나눈다: 청산 다리(→0, 위험 축소)와 신규 다리(0→반대 방향, 위험 증가).
- 포트폴리오 차원(상관된 상품 사이의 상쇄)은 V1에 상관 모델이 없으므로 고려하지 않는다. 상품별 절대 노출로 판단한다.
- 위 분류는 **후보 분류**일 뿐이다. "위험 축소 후보"가 실제로 허용되려면 §6.2.1과 §6.2.2를 모두 통과해야 한다.

#### 6.2.1 위험 축소 주문의 안전 조건 (R1 추가)

위험 축소 후보는 다음을 **모두** 확인한 경우에만 "검증된 위험 축소 주문(verified risk-reducing order)"이 된다. 하나라도 확인하지 못하면 **자동 주문을 차단**하고 사유 코드를 남긴다.

| # | 조건 | 확인하지 못하면 |
|---|---|---|
| S-1 | **실제 보유 포지션 확인**: 주문의 기준 `q_before`가 브로커 기준 보유 수량과 같다 | 차단. 사유 `POSITION_UNCONFIRMED` |
| S-2 | **미체결 및 상태 불명확 주문 확인**: 같은 상품에 미체결 주문이 있으면 §6.3의 최악 경우를 적용한 뒤에도 축소인지 확인한다. 상태 불명확 주문이 있으면 축소 여부를 판단할 수 없다 | 상태 불명확 주문이 있으면 차단. 사유 `UNKNOWN_ORDER_STATE` |
| S-3 | **Reconciliation**: 브로커와 내부의 포지션·미체결 주문·현금이 같은 기준 시각(ADR-0001 §5.1.3)에서 일치한다 | 차단하고 Trading State를 `HALTED`로. 사유 `RECONCILIATION_MISMATCH` |
| S-4 | **주문 후 예상 포지션 검증**: 최악 경우의 주문 후 포지션이 `|q_after| ≤ |q_before|`이고 부호가 바뀌지 않는다. 부호가 바뀌면 청산 다리와 신규 다리로 나누고 신규 다리는 위험 증가로 처리한다 (§6.2) | 차단. 사유 `PROJECTED_POSITION_INVALID` |
| S-5 | **거래 단위**: 수량이 브로커·거래소의 주문 단위(계약 수, lot, 최소 수량)에 맞는다 | 차단. 사유 `INVALID_LOT` |
| S-6 | **계좌 상태**: 계좌가 주문 가능한 상태다 (계좌 자본 > 0, 브로커가 보고한 주문 제한 없음) | 차단. 사유 `ACCOUNT_STATE_INVALID` |
| S-7 | **데이터 신선도**: 주문 판단에 쓴 가격·계좌·포지션 데이터가 허용 지연 안에 있고 ADR-0001 I-1을 만족한다 | 차단. 사유 `STALE_DATA` |

- Backtest에서는 브로커가 없으므로 S-1, S-3이 구성상 성립한다 (내부 상태가 곧 기준). 그래도 S-4, S-5, S-6과 §6.2.2는 Backtest에서도 같은 순수 함수로 검사한다.
- Paper/Live에서는 S-1~S-7을 모두 L3 상태 게이트에서 확인한다.
- 차단된 축소 주문을 사람이 수동으로 낼지는 Trading State와 별도 승인 절차를 따른다 (§6.5).

#### 6.2.2 포트폴리오 전체 검사 (R1 추가)

개별 주문이 위험 축소 주문으로 분류되어도, 주문 후(미체결 주문 최악 경우 포함) 포트폴리오 전체에 대해 다음을 계산한다.

| 지표 `m_k` | 계산 기준 |
|---|---|
| 포트폴리오 gross leverage | Σ 상품별 명목 ÷ 판단 시점 계좌 |
| 전체 margin usage | 증거금 요구량 ÷ 판단 시점 계좌. 증거금 요구량은 증거금 모델이 계산한다 (V1은 계약당 증거금의 단순 합. 브로커·거래소의 포트폴리오 증거금은 다를 수 있음, UNVERIFIED) |
| 상품별 노출 | 상품마다 명목 ÷ 계좌 |
| ETF 사용 가능 현금 | 매수 대금 + 비용 ≤ 사용 가능 현금 − 미체결 매수 예약분 |
| 미체결 주문 최악 경우 노출 | §6.3 |
| 반전 주문의 신규 다리 | §6.2. 신규 다리는 위험 증가 주문의 규칙을 그대로 적용 |

**판정 규칙 (제안)**: 모든 지표 k에 대해 다음 가운데 하나가 성립해야 한다.

```
m_k(after) ≤ L_k            (주문 후 한도 안)
또는
m_k(after) ≤ m_k(before)    (이미 한도 밖이면, 그 지표가 나빠지지 않음)
```

- **한 지표가 줄었다는 이유로 다른 지표가 나빠지는 것을 허용하지 않는다.** 예: 상품 노출과 gross leverage는 줄지만 margin usage가 한도를 넘어 늘어나는 주문 (AT-0003-9).
- 이 규칙은 "한도 안에서 늘어나는 것"은 허용한다. 모든 지표가 조금도 늘지 않아야 하는 더 엄격한 규칙을 쓸지는 Q3-10이다.
- 한도 값이 설정되지 않은 지표가 있으면, Paper/Live에서는 그 지표를 "판단 불가"로 보고 위험 증가 주문을 차단한다 (fail-closed, ADR-0002 §6.4와 같은 원칙).

### 6.3 미체결 주문을 포함한 예상 포지션

```
q_long_worst  = q_filled + Σ(미체결 매수) + (새 매수 주문)
q_short_worst = q_filled − Σ(미체결 매도) − (새 매도 주문)
예상 노출      = max(|q_long_worst|, |q_short_worst|) × |P_ref| × M × fx
```

- 위 식은 **월물(상품) 하나**에 대한 것이다. `M`은 그 월물의 `M[c]`, `fx`는 그 월물 거래통화의 `fx[κ(c)]`다. 포트폴리오 지표는 월물별로 기준통화 금액을 구한 뒤 더한다 (ADR-0001 §6.2와 같은 원칙, R2).

- **상태가 불명확한 주문**(timeout, 응답 유실)은 체결된 것으로 간주해 최악의 경우에 포함한다. **재주문하지 않는다.**
- 미체결 위험 축소 주문은 노출을 줄이는 쪽으로 반영하지 않는다 (체결되지 않을 수 있으므로).
- 상태 불명확 주문이 하나라도 있으면 Trading State는 `HALTED`다 (§6.5). 위 최악 경우 계산은 이때 자동 주문을 내기 위한 것이 아니라, 사람이 상황을 판단할 수 있도록 노출을 보여 주기 위한 것이다.

### 6.4 판단 기준 시점

- 계좌: 판단 시점에 알려진 최신 계좌. 백테스트에서는 전일 종가 기준 계좌를 쓴다. V1 동적 모드의 `opening_account_value`와 같다 (`portfolio_backtest.py:287-289, 331-340`).
- 기준 가격 `P_ref`: 판단 시점에 알려진 가격. 전일 종가를 쓸지 현재 quote를 쓸지, 아니면 둘 중 보수적인 값을 쓸지는 Q3-3이다.
- 사후 검사(A)의 종가 계좌와 당일 quote를 주문 판단에 쓰지 않는다.

### 6.5 거래 상태와 Kill Switch

Trading State는 **계좌(시스템) 단위**다. 상품 단위의 거래 적격성(ADR-0002 Signal Eligibility)과 다른 개념이다.

| 상태 | 자동 주문 | 진입 조건 예 | 해제 |
|---|---|---|---|
| `NORMAL` | 거래 전 위험 검사(L1·L2)를 통과한 주문만 가능. 위험 축소 후보도 §6.2.1·§6.2.2를 통과해야 함 | — | — |
| `RESTRICTED` | **위험 증가 주문 금지.** 검증된 위험 축소 주문(§6.2.1, §6.2.2 통과)만 허용 | 손실·drawdown 한도 도달, 계좌 단위 한도 위반, (Q2-8에 따라) 다수 상품의 데이터 이상 | **원인 해소 확인 + 사용자 승인** (R1 방향) |
| `HALTED` | **자동 주문 금지.** 위험 축소 주문 포함 | Reconciliation 불일치, 상태 불명확 주문, 브로커 연결 이상, 사용자의 수동 Kill Switch | **원인 해소 확인 + 대조 완료 + 사용자 승인** |

- R0는 `RESTRICTED`에서 위험 축소 주문을 조건 없이 허용했다. R1에서는 **검증된** 위험 축소 주문만 허용한다.
- R0의 `RESTRICTED` 진입 조건 가운데 "데이터 신선도 미달, 거래 허용 정책 미달 (ADR-0002)"은 상품 단위의 신호 적격성으로 옮겼다. 그 상품의 위험 증가만 막고 계좌 상태는 바꾸지 않는다.
- **`HALTED`에서의 수동 복구나 수동 축소**는 자동 경로가 아니다. 사람이 상황을 확인하고 별도 승인과 절차(Kill Switch·복구 설계 문서)에 따라 실행한다. 그 절차에서 어떤 주문을 허용할지는 Q3-6이다.
- **해제 원칙 (R1 방향)**: `RESTRICTED`와 `HALTED`는 자동으로 `NORMAL`로 돌아가지 않는다. (1) 원인이 해소되었음을 확인하고, (2) 사용자가 승인한 뒤에만 해제한다. 자동 해제를 허용할 예외가 있는지(예: 일시적 데이터 지연이 풀린 경우)는 Q3-5다.
- 상태 전이는 모두 시각, 원인 코드, 승인자와 함께 기록한다.

**Kill Switch의 범위 (R1 보완)**

Kill Switch는 **두 부분**으로 나눈다.

| 부분 | 내용 | 이 ADR에서의 결정 |
|---|---|---|
| (1) 상태 전이 | 거래 상태를 즉시 `HALTED`로 바꾸고 새 자동 주문 생성을 멈춘다. 내부 동작이며 브로커와 통신하지 않아도 된다 | **정한다** |
| (2) 브로커 복구 절차 | 미체결 주문 처리(취소 여부와 순서), 상태 불명확 주문 조회, 포지션·주문·현금 대조, 사용자 통지, 복구 승인 | **정하지 않는다.** 별도 설계 문서 대상 (CLAUDE.md §8) |

(2)에 대해 이 ADR이 정하는 **제약**만 적는다.

- **모든 주문 일괄 취소를 기본 동작으로 하지 않는다.** 위험 축소 주문까지 취소하면 노출이 남을 수 있다. 어떤 주문을 어떤 순서로 취소할지는 별도 설계에서 정한다. R0의 "위험 증가 주문부터 취소"는 그 설계의 **후보 원칙**으로만 남긴다.
- **통신 단절이나 상태 불명확 주문이 있을 때 자동 재주문을 금지한다.** 취소나 재주문 전에 반드시 상태를 조회한다. 조회할 수 없으면 기다리고 사람에게 알린다.
- 브로커 기준 대조(Reconciliation)가 끝나기 전에는 `HALTED`를 해제하지 않는다.
- 세부 절차와 복구 방법은 **별도 설계 문서**로 작성하고 구현 전에 승인을 받는다. 이 ADR은 상태의 의미와 위 제약만 정한다.

### 6.6 한도 값

leverage, margin, 단일 상품 노출, 손실·drawdown 한도의 **값은 정하지 않는다** (Q3-1). 아래 예제의 한도는 계산을 보여 주기 위한 숫자이며 권고값이 아니다.

## 7. Consequences / Trade-offs

**장점**
- CLAUDE.md §8의 "신규 주문 차단" 요건을 충족하는 구조다.
- 검증된 위험 축소 주문을 허용하므로 한도를 넘은 상태에서도 위험을 줄일 수 있다. 검증 조건 덕분에 잘못된 내부 상태로 "축소"라고 믿고 낸 주문이 실제로는 반전이나 다른 한도 악화가 되는 경우를 막는다 (AT-0003-8, AT-0003-9).

**R1에서 생긴 비용**
- 축소 주문도 막힐 수 있으므로, 위험이 큰 상태에서 자동으로 줄이지 못하는 경우가 생긴다. 이때는 사람이 개입해야 한다. 일간·하루 1회 점검 운영에서는 개입이 늦을 수 있다. 이 위험은 Kill Switch·복구 설계에서 다룬다.
- 포트폴리오 전체 검사에는 증거금 모델이 필요하다. 브로커·거래소의 실제 증거금 계산은 시장 선정 전에는 알 수 없다 (UNVERIFIED).
- 계산(L1, L2)과 상태(L3)를 나눠서 백테스트에서도 같은 정책을 재현할 수 있다.

**단점과 비용**
- 백테스트 결과가 정책 모드에 따라 달라진다. 결과에 정책 모드를 기록해야 한다.
- B는 목표 추종이 덜 되고, C는 새 계산 규칙의 검증 부담이 있다.
- 미체결 주문 모델은 V1에 없다. Paper/Live 이전에는 백테스트에서 미체결이 0이다.
- L3는 브로커가 정해져야 구체화할 수 있다.

## 8. Compatibility with V1

### 8.0 `V1_COMPAT` 적용 범위 (R2, 세 ADR 공통)

> 이 절은 ADR-0001, ADR-0002, ADR-0003에 **같은 내용으로** 들어 있다. 세 ADR의 호환 모드(ADR-0001의 회계 모드, ADR-0002의 정책 프로필, ADR-0003의 사후 검사 모드)는 모두 이 규칙을 따른다. 한 곳을 고치면 세 곳을 함께 고친다.

| 경로 | 규칙 |
|---|---|
| **기존 V1 API** (현재 `src/carver_quant`의 공개 함수. 예: `run_daily_step`, `run_contract_aware_backtest`, `run_ewmac_system_backtest`, `run_prepared_portfolio_backtest`, `run_combined_ewmac_portfolio_backtest`) | 현재의 **입력, 동작, fingerprint를 바꾸지 않는다.** 정책 프로필 인자를 새로 요구하지 않는다. 이 API의 동작이 곧 암묵적 `V1_COMPAT`다 |
| **기존 백테스트 재현** | 기존 V1 API를 그대로 호출(암묵적 `V1_COMPAT`)하거나, 새 API에서 `V1_COMPAT`를 **명시적으로** 선택해 쓸 수 있다 |
| **새 연구 API** (ADR-0001~0003을 구현하는 새 진입점) | 정책 프로필을 **명시적으로** 선택해야 한다 (`RESEARCH`, 또는 재현 목적의 `V1_COMPAT`). **기본값은 없다.** 누락하면 ValueError |
| **Paper/Live** | `V1_COMPAT`를 선택할 수 없다 (ValueError). 허용되는 프로필은 `LIVE`뿐이다. 기존 V1 API는 거래 전 안전 검사가 없으므로 Paper/Live의 주문 경로에서 호출하지 않는다 |
| **우회 금지** | 프로필 누락, 알 수 없는 값, 빈 문자열, `None`, 대소문자 변형 등 어떤 형태로도 기본값이나 `V1_COMPAT`로 대체되지 않는다. Paper/Live에서는 설정 검증 단계에서 시작을 거부한다 (fail-closed) |
| **확인 수준** | 구현 전이므로 기존 306개 테스트 통과, 기존 실행 결과 보존, 기존 fingerprint 보존은 모두 **INFERRED**다. 보존 방법은 P0-03에서 정한다 (ADR-0001 Q1-9) |

### 8.1 그 밖의 영향

| 항목 | 영향 |
|---|---|
| 기존 306개 테스트 | **기존 V1 API는 바꾸지 않는다(사후 검사 A만 사용, 거래 전 정책 없음 = 암묵적 `V1_COMPAT`). 따라서 변경 없음** (INFERRED. 구현 전이므로 회귀 확인 필요). 가드레일 테스트 4개(§3.1)는 그대로 의미가 있다 |

| `risk_guardrail.py`의 계산 함수 | 노출, margin, snapshot 계산은 L1에서 재사용할 수 있다 (INFERRED). 판단 기준 시점과 입력만 다르다 |
| 단일 상품 경로 | V1에는 검사가 없다. 새 정책을 적용할지는 경로 위상 결정(D-02)에 따른다 |
| fingerprint / manifest | 새 연구 API에서 정책 모드와 한도 값을 설정에 넣으면 입력 fingerprint가 바뀐다. 기존 V1 API의 manifest와 fingerprint는 바꾸지 않는다 (§8.0) |

## 9. Financial Integrity Implications

- **Look-ahead**: 거래 전 판단에는 판단 시점까지 알려진 계좌와 가격만 쓴다 (§6.4).
- **경로 의존성**: B는 현재 포지션을 유지하는 정책이라 결과가 이전 경로에 따라 달라진다. 성과를 비교할 때는 같은 정책끼리 비교해야 한다.
- **반올림**: C의 축소는 한도를 지키기 위해 0 쪽 반올림이 필요하다. 이는 V1 목표 반올림(`round_half_away_from_zero`, `position.py:8-18`)과 다른 규칙이다. 새 금융 규칙이므로 CLAUDE.md §3.2의 명세와 독립 계산이 필요하다.
- **미체결과 상태 불명확 주문**: 최악의 경우로 계산하면 이중 주문으로 인한 한도 초과를 막을 수 있다 (AT-0003-3).
- **손실 한도**: 손실·drawdown 한도는 계좌 시계열에서 계산한다. 계좌 평가는 ADR-0001의 회계식을 따른다.

## 10. Acceptance Criteria

공통 가정 (가상의 상품, 실제 사양이 아님): `P_ref` = 350 pt, M = 250,000 IC/pt/ct, fx = 1, 판단 시점 계좌 = 50,000,000 BC.
계약당 명목 = 350 × 250,000 = 87,500,000 → **계약당 leverage 1.75배**. 예제의 한도는 계산 시연용이다.

### AT-0003-1 목표 포지션이 레버리지 한도를 초과하는 경우 (시나리오 4)

- **입력**: 현재 +1 ct (1.75배), 목표 +3 ct (5.25배)
- **기대 출력**:

| 정책 | 한도 L = 3.0 | 한도 L = 4.0 |
|---|---|---|
| A (V1 호환) | +2 체결 후 사후 검사 5.25 > 3.0 → **ValueError (백테스트 중단)** | 5.25 > 4.0 → **ValueError** |
| B | 예상 5.25 > 3.0 → `BLOCK_INCREASE`, 거래 0, +1 유지 (1.75배) | 예상 5.25 > 4.0 → `BLOCK_INCREASE`, 거래 0, +1 유지 |
| C | 최대 = floor(3.0 ÷ 1.75) = 1 → 거래 0, +1 유지 | 최대 = floor(4.0 ÷ 1.75) = 2 → `REDUCE_TO_LIMIT`, **+1 체결**, +2 (3.5배) |

- **여러 한도 결합 (C 모드)**: margin을 계약당 8,000,000, 한도 0.40으로 두면 margin 기준 최대 = floor(0.40 × 50,000,000 ÷ 8,000,000) = floor(2.5) = 2. 적용 최대 = min(leverage 기준 2, margin 기준 2) = 2.
- **전제**: 판단 시점 계좌와 `P_ref`는 §6.4 기준
- **예외**: 계좌 ≤ 0, `P_ref`나 M이 비유한값이면 ValueError (V1 관례)
- **V1 비교**: 호환 모드에서 기존 `test_portfolio_rejects_gross_leverage_limit_breach`가 그대로 통과해야 한다
- **새 테스트 후보**: `test_pretrade_blocks_risk_increasing_order_over_leverage_limit`, `test_reduce_to_limit_rounds_toward_zero`, `test_reduce_to_limit_uses_tightest_constraint`

### AT-0003-2 검증된 위험 축소 주문은 한도 위반 상태에서도 허용 가능

- **입력**: 한도 L = 4.0. 현재 +4 ct (7.0배, 가격이나 계좌 변화로 한도 초과)
- **전제 (R1)**: §6.2.1의 S-1~S-7과 §6.2.2를 모두 통과한 경우의 결과다. 다른 상품이나 다른 지표는 없다고 가정한다. 하나라도 통과하지 못하면 아래 `ALLOW`는 차단으로 바뀐다 (AT-0003-8, AT-0003-9)
- **기대 출력**:

| 목표 | B | C |
|---|---|---|
| +3 (5.25배, 여전히 초과) | 위험 축소이므로 `ALLOW`, −1 체결 → +3 | `REDUCE_TO_LIMIT` → +2 (3.5배) |
| +5 | 위험 증가 → `BLOCK_INCREASE`, +4 유지 | 최대 2 → +2로 축소 (−2 체결) |
| −3 (반전) | 청산 다리 −4 `ALLOW`, 신규 다리 −3 (5.25배) `BLOCK_INCREASE` → **0** | 청산 −4 + 신규 −2 → **−2** (3.5배) |

- **미정**: B에서 한도 초과 상태일 때 목표보다 더 줄이도록 강제할지 (Q3-4)
- **새 테스트 후보**: `test_risk_reducing_order_allowed_when_over_limit`, `test_reversal_split_into_close_and_open_legs`

### AT-0003-3 미체결 주문을 고려하면 한도를 넘는 경우 (시나리오 5)

- **입력**: 한도 L = 4.0. 체결 포지션 +1, 미체결 매수 +1 (이전 주문), 목표 +3
- **기대 출력**:

| 계산 방식 | 새 주문 | 판단에 쓴 예상 포지션 | 판단 leverage | 판정 (L = 4.0) | 미체결까지 모두 체결될 때의 실제 포지션 |
|---|---|---|---|---|---|
| 미체결 무시 (잘못된 방식) | +2 | 1 + 2 = 3 (미체결 +1 누락) | 5.25배 | 5.25 > 4.0 → **거부. 이 한도에서는 결과적으로 차단된다** | (거래했다면) 1 + 1 + 2 = 4 → 7.0배 |
| 미체결 포함 (B) | +1 후보 | 1 + 1 + 1 = 3 | 5.25배 > 4.0 | `BLOCK_INCREASE` → 새 주문 없음. 예상 +2 = 3.5배 | 2 → 3.5배 |
| 미체결 포함 (C) | 최대 2 − 예상 2 = 0 | 2 | 3.5배 | 새 주문 없음 | 2 → 3.5배 |

- **L = 4.0과 L = 6.0의 차이**: 미체결을 무시하는 방식은 예상 포지션을 실제 최악 경우(4 ct, 7.0배)보다 작게(3 ct, 5.25배) 본다. 이 과소평가가 판정을 바꾸는 것은 **한도가 그 사이에 있을 때**뿐이다.
  - L = 4.0: 과소평가한 5.25배도 한도를 넘으므로 거부된다. 판정은 올바른 방식과 같다. **다만 판단 근거(예상 포지션 3 ct)는 틀렸다.**
  - L = 6.0: 과소평가한 5.25배는 한도 안이라 +2를 허용한다. 미체결까지 체결되면 7.0배가 되어 **한도 초과를 놓친다.** 올바른 방식은 +1만 허용한다 (AT-0003-10).
  - 일반적으로 "≤ 한도면 허용"으로 비교할 때, 이 사례에서 놓침이 생기는 한도 범위는 5.25 ≤ L < 7.0이다. 비교 기호(≤ 또는 <)는 아직 정하지 않았다 (AT-0003-4의 미정 사항과 같음).
- **변형**: 미체결 매수 +1의 상태가 *불명확*(timeout)하면 체결된 것으로 간주한다(같은 결과). **재주문하지 않고** 상태를 조회한다.
- **새 테스트 후보**: `test_open_orders_included_in_projected_exposure`, `test_unknown_status_order_treated_as_filled_and_not_resubmitted`

### AT-0003-8 내부 포지션과 브로커 포지션이 불일치하는 경우 (R1 추가, 인수 테스트 명세 4)

공통 가정(§10 첫 부분)과 같다: 계약당 1.75배, 계좌 50,000,000.

- **입력**: 내부 포지션 +3 ct. 브로커가 보고한 포지션 +2 ct (예: 내부에 기록되지 않은 부분 체결 취소, 사용자의 수동 거래). 미체결 주문 없음. 두 값은 같은 기준 시각의 값이다. 목표 0 (전량 청산)
- **기대 출력**:

| 항목 | 결과 |
|---|---|
| Reconciliation (S-3) | 불일치 (+3 ≠ +2). 허용 오차는 0 ct (계약 수는 정수) |
| Trading State | `HALTED`, 사유 `RECONCILIATION_MISMATCH` |
| 자동 주문 | **없음.** 축소 주문(−3)도 내지 않음 |
| 계좌 평가 | 계속함. 내부 값과 브로커 값을 모두 기록하고 불일치를 표시 |
| 사용자 통지 | 있음. 복구는 별도 절차와 승인 |

- **판단 근거**: 내부 기준으로 −3을 내면 브로커 포지션은 +2 − 3 = **−1**이 된다. "청산" 주문이 1.75배의 **새 매도 포지션**을 만든다. S-1과 S-3이 이 오류를 막는다. 목표가 +1인 변형에서는 내부 기준 −2 주문이 브로커 포지션을 0으로 만들어 목표와 달라진다. 이 경우도 같은 이유로 막는다
- **예외조건**:
  - 브로커 조회가 실패하거나 timeout이면 "일치"로 가정하지 않는다. 상태 불명확으로 보고 `HALTED`
  - 기준 시각이 다른 두 값을 비교하지 않는다. 평가 경계 이후의 체결(ADR-0001 §5.1.3) 때문에 생긴 차이는 같은 시각으로 맞춘 뒤 다시 비교한다
  - Backtest에서는 브로커가 없으므로 이 검사는 Paper/Live L3 테스트에서만 의미가 있다 (모의 브로커 응답 사용)
- **새 테스트 후보**: `test_position_mismatch_halts_and_blocks_reducing_order`, `test_broker_query_failure_is_not_treated_as_match`

### AT-0003-9 위험 축소 주문이 다른 위험 한도를 위반하는 경우 (R1 추가, 인수 테스트 명세 5)

이 테스트에는 증거금 모델 주입이 필요하다. 아래 증거금 값은 **가상의 포트폴리오 증거금 모델**이다. 특정 거래소·브로커의 실제 규칙이 아니다 (UNVERIFIED). V1의 `calculate_margin_required`는 계약당 증거금의 단순 합이라서 이 상황을 표현할 수 없다.

- **입력**:
  - 계좌 50,000,000. 같은 기초자산의 두 월물 A, B. 각각 가격 400 pt, M = 25,000 IC/pt/ct → **계약당 명목 10,000,000 (0.2배)**
  - 현재: A +2 ct, B −2 ct (calendar spread)
  - 가상의 증거금 모델: 스프레드 한 쌍(A +1, B −1)당 1,500,000. 단독 포지션은 계약당 8,000,000
  - 시연용 한도: gross leverage 4.0, margin usage 0.30
  - 주문 후보: B +2 (B −2 → 0). 상품 B만 보면 위험 축소 후보
- **기대 출력**:

| 지표 | 주문 전 | 주문 후 | 한도 | 판정 |
|---|---|---|---|---|
| B 상품 노출 | 0.4배 | 0 | — | 감소 |
| gross leverage | 4 × 10,000,000 ÷ 50,000,000 = **0.8배** | 2 × 10,000,000 ÷ 50,000,000 = **0.4배** | 4.0 | 감소 |
| margin 요구량 | 2쌍 × 1,500,000 = 3,000,000 | A 단독 2 × 8,000,000 = 16,000,000 | — | — |
| margin usage | **6%** | **32%** | 30% | **한도 초과로 증가 → 위반** |

  결과: **자동 주문 차단**, 사유 `REDUCING_ORDER_WORSENS_MARGIN`. 노출과 leverage가 줄어도 margin usage 악화를 상쇄하지 않는다 (§6.2.2)
- **참고 (결정 아님)**: B +1만 낼 경우 A +2, B −1 → 1쌍 1,500,000 + A 단독 1 × 8,000,000 = 9,500,000 → **19%** ≤ 30%, gross 0.6배. C 모드에서 이런 부분 축소를 제안할지는 Q3-8, Q3-10과 함께 정한다
- **변형 (ETF 현금)**: ETF −1,000주(공매도) 보유, 가격 10,000, 상환 매수 1,000주 = 10,000,000 + 비용. 사용 가능 현금 6,000,000이면 노출은 줄어도 현금 지표가 위반되므로 차단. 대상 시장에서 ETF 공매도가 가능한지는 UNVERIFIED
- **판단 근거**: §6.2.2 판정 규칙
- **예외조건**: 증거금 모델이 없거나 판단 시점 계좌 ≤ 0이면 ValueError (Backtest) 또는 차단 (Paper/Live, fail-closed)
- **새 테스트 후보**: `test_reducing_order_blocked_when_margin_usage_worsens_over_limit`, `test_reducing_order_blocked_when_cash_insufficient`

### AT-0003-10 미체결 주문과 신규 주문을 합하면 한도를 넘는 경우 (R1 추가, 인수 테스트 명세 6)

AT-0003-3의 숫자를 인수 테스트 명세 형식으로 정리하고 변형을 더한다. 공통 가정은 §10 첫 부분과 같다 (계약당 1.75배).

- **입력 (기본)**: 체결 포지션 +1, 미체결 매수 +1 (이전 주문, 상태 확인됨), 목표 +3. 한도는 두 가지로 본다
- **기대 출력**:

| 한도 | 올바른 계산 (미체결 포함) | 잘못된 계산 (미체결 무시) |
|---|---|---|
| L = 4.0 | 새 주문 후보 = 3 − 1 − 1 = +1, `q_long_worst` = 1 + 1 + 1 = 3 → 5.25배 > 4.0 → `BLOCK_INCREASE`, 새 주문 없음 | 새 주문 +2, 계산상 1 + 2 = 3 → 5.25배 > 4.0 → 거부. **이 한도에서는 결과가 같다** (AT-0003-3) |
| L = 6.0 | 후보 +1, `q_long_worst` = 3 → 5.25배 ≤ 6.0 → `ALLOW` +1. 미체결이 체결되면 +3 (5.25배) | 새 주문 +2, 계산상 3 → 5.25배 ≤ 6.0 → 허용. 그러나 미체결 +1까지 체결되면 1 + 1 + 2 = **4 ct = 7.0배 > 6.0. 한도 초과를 놓친다** |
- **변형 1 (미체결 매도는 상쇄하지 않음)**: 체결 +2, 미체결 매도 −1, 새 매수 후보 +1
  - 올바른 계산: `q_long_worst` = 2 + 0 + 1 = **3** → 5.25배 > 4.0 → `BLOCK_INCREASE`
  - 잘못된 계산(미체결 매도를 상쇄): 2 − 1 + 1 = 2 → 3.5배 → 허용해 버림. 미체결 매도가 체결되지 않으면 실제 포지션이 +3이 된다
- **변형 2 (상태 불명확)**: 미체결 매수 +1의 상태가 timeout으로 불명확 → 최악 경우에 체결로 포함하고, Trading State `HALTED` (§6.5). 새 주문 없음, **재주문 없음**
- **판단 근거**: §6.3. 미체결 위험 축소 주문은 체결되지 않을 수 있으므로 노출을 줄이는 쪽으로 반영하지 않는다
- **예외조건**: 미체결 주문 목록을 조회할 수 없으면 차단 (S-2). 미체결 수량이 정수가 아니거나 방향 정보가 없으면 ValueError
- **새 테스트 후보**: `test_open_buy_and_new_buy_exceed_limit`, `test_open_sell_not_netted_against_new_buy`
