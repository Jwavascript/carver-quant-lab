# ADR-0003: 거래 전 위험 검사 정책 (Pre-trade Risk Policy)

## 1. Title

### 3.2 문제

- CLAUDE.md §8은 "위험 한도를 위반하면 신규 주문을 차단한다"고 요구한다. V1은 주문을 차단하지 않고 사후에 실패한다.
- 사후 검사의 기준(종가 계좌, 당일 quote)은 주문 시점에 알 수 없는 정보다. 백테스트의 일관성 검사로는 쓸 수 있지만, 주문 판단 기준으로 옮기면 look-ahead가 된다 (INFERRED).
- V1은 미체결 주문 개념이 없다. 새 포지션 = 목표 포지션(전량 체결 가정)이다 (`contract_aware_daily_step.py:266`).

## 4. Decision Drivers

1. **제한된 손실 허용**: 한도를 넘는 위험을 미리 막는다.
2. **위험 축소는 막지 않음**: 한도를 넘은 상태에서 포지션을 줄이는 주문까지 막으면 위험이 더 커진다.
3. **시점 무결성**: 주문 판단에는 주문 시점에 알 수 있는 계좌와 가격만 쓴다.
4. **모드 간 공유**: 위험 *계산*은 Backtest/Paper/Live가 같은 순수 함수를 쓴다 (CLAUDE.md §4).
5. **결정론과 감사 가능성**: 같은 입력이면 같은 결정이 나오고, 거부·축소 사유가 기록되어야 한다.
6. **V1 호환성**: 기존 가드레일 테스트를 보존할 수 있어야 한다.

## 5. Considered Options

### 5.1 대안 A — 기존 사후 검사 유지

- 내용: 거래 후 검사하고 위반하면 중단한다.
- 장점: 변경이 없다. 백테스트 설정 오류를 바로 알려 준다.
- 단점: 주문을 막지 못한다. Live에는 쓸 수 없다. 백테스트 하나가 위반 하루 때문에 통째로 실패하므로 연구에 불편하다.

### 5.2 대안 B — 주문 전 예상 위험 검사, 위반 시 위험 증가 주문 거부

- 내용: 주문 후 예상 포지션(미체결 포함)으로 위험을 계산한다. 한도를 넘으면 **위험을 늘리는 주문을 거부**하고 현재 포지션을 유지한다.
- 장점: 단순하고 보수적이다. 결정이 이진적이라 설명하기 쉽다.
- 단점: 목표가 한도를 조금만 넘어도 증가분 전체를 거부하므로 목표 추종이 덜 된다. 증가분의 일부는 한도 안에 들어갈 수 있는데도 거부된다.

### 5.3 대안 C — 한도를 넘는 목표를 허용 범위로 축소한 뒤 주문

- 내용: 한도를 만족하는 최대 수량으로 목표를 줄인다. 이때 반올림은 0 쪽(toward zero)으로 한다.
- 장점: 한도 안에서 목표에 가장 가깝게 따라간다.
- 단점: 새로운 포지션 계산 규칙이 생긴다. 금융 공식 추가에 해당하므로 명세와 독립 검증이 필요하다. 여러 한도와 여러 상품이 걸려 있으면 축소량을 어떻게 배분할지 정해야 한다. 원래 목표의 반올림 규칙(`round_half_away_from_zero`)과 다른 규칙이 섞인다.

### 5.4 위험 요소별 분류

| 위험 요소 | V1 백테스트 | 공유 순수 계산 (Backtest/Paper/Live) | Live 전용 상태 검증 |
|---|---|---|---|
| Gross leverage | 있음 (사후) | 예상 포지션 기준 계산 | — |
| Margin usage | 있음 (사후) | 예상 포지션 기준 계산 | 브로커가 보고한 증거금과 대조 |
| 계좌 자본 > 0 | snapshot 계산 시에만 | 판단 시점 계좌가 양수인지 | 브로커 계좌 잔고 대조 |
| 최대 단일 상품 노출 | 없음 | 상품별 명목 ÷ 계좌 | — |
| 데이터 신선도 | 없음 | 입력으로 받은 타임스탬프로 판정 (ADR-0001) | 데이터 수신 상태 모니터링 |
| 최소 거래 수량, 반올림 | 정수 반올림만 | lot 단위 반올림, C의 0쪽 반올림 | 브로커 주문 단위 확인 |
| 현금 부족 (ETF) | 없음 | 매수 대금 + 비용 ≤ 사용 가능 현금 − 미체결 매수 예약분 | 브로커 주문 가능 금액 대조 |
| 미체결 포함 예상 포지션 | 없음 (전량 체결) | 최악 경우 노출 계산 (§6.3) | 미체결 주문 목록을 브로커에서 조회 |
| 손실·drawdown 한도 | 없음 | 계좌 시계열로 계산 | — |
| 브로커–내부 상태 불일치 | 없음 | — | **Reconciliation** (CLAUDE.md §8) |
| 주문 상태 불명확 (timeout 등) | 없음 | — | 재주문 금지, 상태 조회 후 대조 (CLAUDE.md §8) |

## 6. Proposed Decision

### 6.1 결정 요지

**B를 기본 정책으로 제안한다. 위험을 늘리는 주문은 한도를 위반하면 거부하고, 위험을 줄이는 주문은 한도 위반 상태에서도 허용한다. C(한도까지 축소)는 명시적으로 켜는 선택 모드로 두고, 기본값으로 할지는 P0-04의 수치 검증 후 사용자가 결정한다. A(사후 검사)는 V1 호환 모드에서 일관성 검사로만 유지한다.**

구조는 세 층이다.

| 층 | 내용 | 성격 |
|---|---|---|
| L1 위험 계산 | 예상 포지션, 노출, leverage, margin, 단일 상품 노출, 현금 요구량, drawdown, 신선도 판정 | 순수 함수. 세 모드 공유 |
| L2 정책 결정 | 주문 후보별로 `ALLOW` / `REDUCE_TO_LIMIT`(C 모드) / `BLOCK_INCREASE`와 사유 코드 결정 | 순수 함수. 세 모드 공유 |
| L3 상태 게이트 | 거래 상태 `NORMAL` / `RESTRICTED` / `HALTED` 결정 (브로커 대조, 주문 상태, 데이터 수신) | Paper/Live 전용 (Imperative Shell) |

**처리 순서**: 목표 포지션 (V1 사이징) → 버퍼링 → 거래 허용 판단 (ADR-0002) → **L2 정책** → L3 게이트 → 주문

### 6.2 위험 증가와 위험 축소의 분류

- 주문 후보 하나를 기준으로, `|q_after| ≤ |q_before|`이고 부호가 바뀌지 않으면 **위험 축소**다.
- 부호가 바뀌는 반전 주문은 두 다리로 나눈다: 청산 다리(→0, 위험 축소)와 신규 다리(0→반대 방향, 위험 증가).
- 포트폴리오 차원(상관된 상품 사이의 상쇄)은 V1에 상관 모델이 없으므로 고려하지 않는다. 상품별 절대 노출로 판단한다.

### 6.3 미체결 주문을 포함한 예상 포지션

```
q_long_worst  = q_filled + Σ(미체결 매수) + (새 매수 주문)
q_short_worst = q_filled − Σ(미체결 매도) − (새 매도 주문)
예상 노출      = max(|q_long_worst|, |q_short_worst|) × |P_ref| × M × fx
```

- **상태가 불명확한 주문**(timeout, 응답 유실)은 체결된 것으로 간주해 최악의 경우에 포함한다. **재주문하지 않는다.**
- 미체결 위험 축소 주문은 노출을 줄이는 쪽으로 반영하지 않는다 (체결되지 않을 수 있으므로).

### 6.4 판단 기준 시점

- 계좌: 판단 시점에 알려진 최신 계좌. 백테스트에서는 전일 종가 기준 계좌를 쓴다. V1 동적 모드의 `opening_account_value`와 같다 (`portfolio_backtest.py:287-289, 331-340`).
- 기준 가격 `P_ref`: 판단 시점에 알려진 가격. 전일 종가를 쓸지 현재 quote를 쓸지, 아니면 둘 중 보수적인 값을 쓸지는 Q3-3이다.
- 사후 검사(A)의 종가 계좌와 당일 quote를 주문 판단에 쓰지 않는다.

### 6.5 거래 상태와 Kill Switch

| 상태 | 자동 신규 주문 | 위험 축소 주문 | 진입 조건 예 | 해제 |
|---|---|---|---|---|
| `NORMAL` | 허용 (L2 정책 적용) | 허용 | — | — |
| `RESTRICTED` | **위험 증가 금지** | 허용 | 손실·drawdown 한도 도달, 데이터 신선도 미달, 거래 허용 정책 미달 (ADR-0002) | 조건이 해소되고 규칙에 따라 해제. 사용자 승인 필요 여부는 Q3-5 |
| `HALTED` | **금지** | 자동으로는 금지. 사용자 승인을 받은 수동 축소만 허용할지는 Q3-6 | Reconciliation 불일치, 상태 불명확 주문 발생, 브로커 연결 이상, 사용자의 수동 Kill Switch | **사용자 승인** + 대조 완료 |

**Kill Switch의 정의**: Kill Switch는 "모든 주문을 즉시 취소"하는 기능이 아니다. 거래 상태를 `HALTED`로 전환하고 정해진 절차를 실행하는 것이다. 절차는 다음을 포함해야 한다.

1. 새 자동 주문 생성을 멈춘다.
2. 미체결 주문을 **위험 증가 주문과 위험 축소 주문으로 구분**한다. 취소는 위험 증가 주문부터 한다. 위험 축소 주문까지 일괄 취소하면 노출이 남을 수 있다.
3. 상태가 불명확한 주문은 취소나 재주문을 하기 전에 **상태를 먼저 조회**한다.
4. 브로커 기준으로 포지션, 주문, 현금을 대조한다.
5. 사용자에게 알리고, 복구는 사용자가 승인한다.

세부 절차와 복구 방법은 CLAUDE.md §8에 따라 **별도 설계 문서**로 작성하고 구현 전에 승인을 받는다. 이 ADR은 상태의 의미만 정한다.

### 6.6 한도 값

leverage, margin, 단일 상품 노출, 손실·drawdown 한도의 **값은 정하지 않는다** (Q3-1). 아래 예제의 한도는 계산을 보여 주기 위한 숫자이며 권고값이 아니다.

## 7. Consequences / Trade-offs

**장점**
- CLAUDE.md §8의 "신규 주문 차단" 요건을 충족하는 구조다.
- 위험 축소 주문을 허용하므로 한도를 넘은 상태에서 더 나빠지지 않는다.
- 계산(L1, L2)과 상태(L3)를 나눠서 백테스트에서도 같은 정책을 재현할 수 있다.

**단점과 비용**
- 백테스트 결과가 정책 모드에 따라 달라진다. 결과에 정책 모드를 기록해야 한다.
- B는 목표 추종이 덜 되고, C는 새 계산 규칙의 검증 부담이 있다.
- 미체결 주문 모델은 V1에 없다. Paper/Live 이전에는 백테스트에서 미체결이 0이다.
- L3는 브로커가 정해져야 구체화할 수 있다.

## 8. Compatibility with V1

| 항목 | 영향 |
|---|---|
| 기존 306개 테스트 | **V1 호환 모드(사후 검사 A만 사용, 거래 전 정책 끔)를 기본값으로 쓰면 변경 없음.** 가드레일 테스트 4개(§3.1)는 그대로 의미가 있다 |
| `risk_guardrail.py`의 계산 함수 | 노출, margin, snapshot 계산은 L1에서 재사용할 수 있다 (INFERRED). 판단 기준 시점과 입력만 다르다 |
| 단일 상품 경로 | V1에는 검사가 없다. 새 정책을 적용할지는 경로 위상 결정(D-02)에 따른다 |
| fingerprint / manifest | 정책 모드와 한도 값을 설정에 넣으면 입력 fingerprint가 바뀐다. 호환 모드에서는 기존 값을 유지해야 한다 |

## 9. Financial Integrity Implications

- **Look-ahead**: 거래 전 판단에는 판단 시점까지 알려진 계좌와 가격만 쓴다 (§6.4).
- **경로 의존성**: B는 현재 포지션을 유지하는 정책이라 결과가 이전 경로에 따라 달라진다. 성과를 비교할 때는 같은 정책끼리 비교해야 한다.
- **반올림**: C의 축소는 한도를 지키기 위해 0 쪽 반올림이 필요하다. 이는 V1 목표 반올림(`round_half_away_from_zero`, `position.py:8-18`)과 다른 규칙이다. 새 금융 규칙이므로 CLAUDE.md §3.2의 명세와 독립 계산이 필요하다.
- **미체결과 상태 불명확 주문**: 최악의 경우로 계산하면 이중 주문으로 인한 한도 초과를 막을 수 있다 (AT-0003-3).
- **손실 한도**: 손실·drawdown 한도는 계좌 시계열에서 계산한다. 계좌 평가는 ADR-0001의 회계식을 따른다.

## 10. Acceptance Criteria

공통 가정 (가상의 상품, 실제 사양이 아님): `P_ref` = 350 pt, M = 250,000 IC/pt/ct, fx = 1, 판단 시점 계좌 = 50,000,000 BC.
계약당 명목 = 350 × 250,000 = 87,500,000 → **계약당 leverage 1.75배**. 예제의 한도는 계산 시연용이다.

### AT-0003-1 목표 포지션이 레버리지 한도를 초과하는 경우 (시나리오 4)

- **입력**: 현재 +1 ct (1.75배), 목표 +3 ct (5.25배)
- **기대 출력**:

| 정책 | 한도 L = 3.0 | 한도 L = 4.0 |
|---|---|---|
| A (V1 호환) | +2 체결 후 사후 검사 5.25 > 3.0 → **ValueError (백테스트 중단)** | 5.25 > 4.0 → **ValueError** |
| B | 예상 5.25 > 3.0 → `BLOCK_INCREASE`, 거래 0, +1 유지 (1.75배) | 예상 5.25 > 4.0 → `BLOCK_INCREASE`, 거래 0, +1 유지 |
| C | 최대 = floor(3.0 ÷ 1.75) = 1 → 거래 0, +1 유지 | 최대 = floor(4.0 ÷ 1.75) = 2 → `REDUCE_TO_LIMIT`, **+1 체결**, +2 (3.5배) |

- **여러 한도 결합 (C 모드)**: margin을 계약당 8,000,000, 한도 0.40으로 두면 margin 기준 최대 = floor(0.40 × 50,000,000 ÷ 8,000,000) = floor(2.5) = 2. 적용 최대 = min(leverage 기준 2, margin 기준 2) = 2.
- **전제**: 판단 시점 계좌와 `P_ref`는 §6.4 기준
- **예외**: 계좌 ≤ 0, `P_ref`나 M이 비유한값이면 ValueError (V1 관례)
- **V1 비교**: 호환 모드에서 기존 `test_portfolio_rejects_gross_leverage_limit_breach`가 그대로 통과해야 한다
- **새 테스트 후보**: `test_pretrade_blocks_risk_increasing_order_over_leverage_limit`, `test_reduce_to_limit_rounds_toward_zero`, `test_reduce_to_limit_uses_tightest_constraint`

### AT-0003-2 위험 축소 주문은 한도 위반 상태에서도 허용

- **입력**: 한도 L = 4.0. 현재 +4 ct (7.0배, 가격이나 계좌 변화로 한도 초과)
- **기대 출력**:

| 목표 | B | C |
|---|---|---|
| +3 (5.25배, 여전히 초과) | 위험 축소이므로 `ALLOW`, −1 체결 → +3 | `REDUCE_TO_LIMIT` → +2 (3.5배) |
| +5 | 위험 증가 → `BLOCK_INCREASE`, +4 유지 | 최대 2 → +2로 축소 (−2 체결) |
| −3 (반전) | 청산 다리 −4 `ALLOW`, 신규 다리 −3 (5.25배) `BLOCK_INCREASE` → **0** | 청산 −4 + 신규 −2 → **−2** (3.5배) |

- **미정**: B에서 한도 초과 상태일 때 목표보다 더 줄이도록 강제할지 (Q3-4)
- **새 테스트 후보**: `test_risk_reducing_order_allowed_when_over_limit`, `test_reversal_split_into_close_and_open_legs`

### AT-0003-3 미체결 주문을 고려하면 한도를 넘는 경우 (시나리오 5)

- **입력**: 한도 L = 4.0. 체결 포지션 +1, 미체결 매수 +1 (이전 주문), 목표 +3
- **기대 출력**:

| 계산 방식 | 새 주문 | 최악의 경우 포지션 | leverage | 판정 |
|---|---|---|---|---|
| 미체결 무시 (잘못된 방식) | +2 | 1 + 1 + 2 = 4 | **7.0배** | 한도를 넘었는데도 놓침 |
| 미체결 포함 (B) | +1 후보 | 1 + 1 + 1 = 3 | 5.25배 > 4.0 | `BLOCK_INCREASE` → 새 주문 없음. 예상 +2 = 3.5배 |
| 미체결 포함 (C) | 최대 2 − 예상 2 = 0 | 2 | 3.5배 | 새 주문 없음 |

- **변형**: 미체결 매수 +1의 상태가 *불명확*(timeout)하면 체결된 것으로 간주한다(같은 결과). **재주문하지 않고** 상태를 조회한다.
- **새 테스트 후보**: `test_open_orders_included_in_projected_exposure`, `test_unknown_status_order_treated_as_filled_and_not_resubmitted`

### AT-0003-4 Drawdown 한도 → RESTRICTED

- **입력**: 계좌 최고치 50,000,000, 현재 45,000,000 → drawdown 10%. 시연용 한도 D = 10%
- **기대 출력**: 상태 `RESTRICTED`. 위험 증가 주문은 `BLOCK_INCREASE`, 위험 축소 주문은 `ALLOW`
- **전제**: drawdown 정의는 V1 `calculate_drawdowns`와 같다 (`(equity − 최고치) ÷ 최고치`, `performance.py:130-170`)
- **미정**: 비교 기호(≥ 또는 >), 해제 조건 (Q3-5)
- **새 테스트 후보**: `test_drawdown_limit_restricts_to_reduce_only`

### AT-0003-5 데이터 신선도

- **입력**: 판단 시점 기준으로 최신 가격의 `data_available_at`이 허용 지연을 넘음
- **기대 출력**: 해당 상품은 `RESTRICTED`, 위험 증가 주문 차단, 사유 `STALE_DATA`. 허용 지연 값은 미정
- **새 테스트 후보**: `test_stale_data_blocks_risk_increase`

### AT-0003-6 현금 부족 (ETF, 명세만)

- **입력**: 사용 가능 현금 1,000,000. 미체결 매수 예약 300,000. 새 매수 대금 + 예상 비용 800,000
- **기대 출력**: 1,000,000 − 300,000 = 700,000 < 800,000 → B: `BLOCK_INCREASE`. C: 700,000 이하가 되도록 수량을 0 쪽으로 축소
- **미정**: 매도 대금을 결제 전에 쓸 수 있는지 (Q3-7)

### AT-0003-7 V1 호환

- 호환 모드에서 306개 테스트가 기대값 수정 없이 통과해야 한다.
- 정책을 켜지 않은 포트폴리오 백테스트의 입력·결과 fingerprint가 기존 값과 같아야 한다.
