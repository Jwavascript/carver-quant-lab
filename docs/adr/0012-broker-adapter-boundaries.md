**승인된 원칙**

1. 공통 Broker Adapter port와 브로커별 구현을 분리한다 (§6.1, §6.2).
2. Paper 시뮬레이터도 같은 port 계약을 쓴다 (§6.7).
3. 금융 코어는 브로커 SDK를 직접 호출하지 않는다 (§5.1, ADR-0004 R-3).
4. 지금 단계에서 별도 상주 주문 라우팅 서비스를 도입하지 않는다 (§6.1, Q12-9).
5. 주문 제출 전 제출 시도 기록(write-ahead)을 영속화하고 성공을 확인한다 (BR-3 (1)~(3)).
6. 영속화 실패나 확인 불가 상태에서는 주문을 보내지 않는다 (BR-3 (3)).
7. 제출 시도 기록과 실제 제출·접수 상태를 구분한다. 전송 확정 지점을 넘기 전에는 `PENDING_SUBMIT`으로 바꾸지 않는다 (BR-3 (4)).
8. 쓰기 요청 결과를 `NOT_SENT` / `REJECTED` / `ACKNOWLEDGED` / `UNKNOWN`으로 구분한다 (BR-2).
9. 미전송을 증명하지 못한 timeout은 `UNKNOWN`이다 (BR-2).
10. 상태 불명확 주문을 자동으로 재제출하지 않는다 (BR-4, ADR-0009 R9-5).
11. 전송 계층의 암묵적 자동 재전송을 금지한다 (BR-5).
12. 상태 불명확 주문의 노출은 ACCEPTED ADR-0003 §6.3·ADR-0009 §6.2의 보수적 규칙(전량 체결 간주)으로 계산한다 (BR-12, AT-0012-5).
13. 체결 ID 기반 멱등 반영과 중복·충돌 검사를 적용한다 (§6.6, ADR-0009 §6.4a).
14. 취소·정정 결과와 체결 통보의 불일치는 ACCEPTED ADR-0009 RP-1~RP-5를 따른다 (BR-12, BF-10).
15. 연결 이상과 대조 불일치에 대한 ACCEPTED ADR-0003의 `HALTED` 규칙을 완화하지 않는다 (§6.3a, §6.5, BR-8~BR-10).
16. 재시작 시 내부 기록만 믿지 않고 브로커 상태를 조회·대조한다 (BR-3 (6), BR-8).
17. Live에 필수적인 기능을 검증할 수 없는 Broker Adapter로는 Live 시작을 거부한다 (BR-1).
18. Adapter는 브로커 데이터를 번역·기록하지만 핵심 금융 위험 판단을 하지 않는다 (BR-6).
19. Live 활성화와 Kill Switch 수동 복구에는 별도 설계와 사용자 승인이 필요하다 (§6.8, CLAUDE.md §8).

**R1 정정의 보존**: AT-0012-5의 `UNKNOWN` 최악 경우 롱은 **+5**(원래 주문 전량)이며 max(2, 3) = 3으로 줄이지 않는다. 늦은 체결로 실제 포지션이 +3이 되어도 주문 종료 확인과 대조 전에는 이 상한을 유지하고, 원인 확인 + 대조 완료 + 사용자 승인 전까지 `HALTED`다. AT-0012-6의 비원자적 정정 최악 경우는 **+13**이고 정정 timeout은 `UNKNOWN`·`HALTED`다. 제출 시도 기록은 영속화 확인 전 전송을 금지하며, 비정상 종료와 기록 유실의 잔여 위험을 그대로 기록한다 (BR-3).

### 3.2 이미 승인된 규칙 (ACCEPTED, 이 ADR은 바꾸지 않음)

| 질문 | 내용 |
|---|---|
| Q9-1 | 브로커의 Client Order ID 멱등 지원, 체결 ID 제공 여부, 상태·취소 API 의미, 브로커 상태와 내부 상태의 대응 |
| Q9-10 | 정정의 원자성, 정정 수량의 의미(누적 / 남은), 정정 응답과 체결 통보의 순서 보장 |
| Q9-11 | 체결 ID의 고유성 범위(계좌, 주문, 날짜), 체결 정정·취소 이벤트의 형식 |
| §6.4 | 브로커가 체결 ID를 주지 않을 때의 대체 키. 정하기 전에는 그 브로커를 Live에 쓰지 않는다 |

### 3.4 브로커마다 다를 수 있는 것 (모두 UNVERIFIED)

Client Order ID를 받는지와 중복 방지 키로 인정하는지, Client Order ID로 조회할 수 있는지, 체결 ID의 존재와 고유성 범위, 체결 통보의 순서·중복·누락 보장, 이벤트 순번의 존재, 정정의 원자성과 수량 의미, 포지션·현금 보고의 지연과 기준 시각 제공 여부, 증거금 조회, 세션 상태 조회, 장 밖 주문 접수(ADR-0007 Q7-9), 요청 빈도 제한, 재연결 후 놓친 이벤트의 재전송, SDK의 자동 재시도 동작, 수수료 통화 보고 (ADR-0008 Q8-11).

## 4. Decision Drivers

1. **가용성보다 안전**: 확인할 수 없으면 주문하지 않는다 (fail-closed). 브로커가 응답하지 않는 것을 "주문 없음"으로 해석하지 않는다.
2. **승인된 규칙 준수**: ADR-0003, ADR-0009의 상태와 해제 원칙을 바꾸지 않는다.
3. **브로커 가정 금지**: 기능이 확인되지 않으면 없는 것으로 설계한다.
4. **테스트 가능성**: Paper 시뮬레이터가 같은 계약으로 실패를 재현할 수 있어야 한다.
5. **책임 분리**: Adapter는 번역과 결과 분류만 한다. 금융 계산과 상태 결정은 엔진과 코어가 한다 (ADR-0004 R-3).
6. **개인 운영 비용**: 하루 1회 점검, 단일 계좌, 2,000만~5,000만 원 규모에 맞는 복잡도 (CLAUDE.md §1).
7. **비밀정보 보호**: 자격증명은 코드·로그·문서·커밋에 남기지 않는다 (CLAUDE.md §5).

## 5. Considered Options

### 5.1 대안 A — 브로커 SDK를 금융 엔진에서 직접 호출

- **내용**: 엔진이나 코어 함수가 브로커 SDK를 직접 import해 주문·조회한다.
- **장점**: 코드가 가장 짧다.
- **단점**: ACCEPTED ADR-0004 R-3, CLAUDE.md §4를 어긴다. 백테스트·연구 코드에서 실제 주문이 나갈 경로가 생긴다. 브로커를 바꾸면 엔진 전체가 바뀐다. 실패를 시뮬레이터로 재현하기 어렵다.

### 5.2 대안 B — 공통 Broker Adapter 계약과 브로커별 구현

- **내용**: 프로젝트가 정한 계약(port)을 두고 브로커마다 구현한다. 엔진은 계약만 안다. Paper 시뮬레이터도 같은 계약을 구현한다.
- **장점**: 브로커 교체가 Adapter 교체로 끝난다. 시뮬레이터로 실패를 재현할 수 있다. 실주문 호출 위치를 한 곳으로 제한할 수 있다 (ADR-0010 PK-11).
- **단점**: 계약을 브로커 공통분모로 잡으면 브로커 고유 기능을 쓰기 어렵다. 그래서 기능 선언(§6.3)이 필요하다.

### 5.3 대안 C — B + 별도 주문 라우팅·영속 상태 관리 서비스

- **내용**: 주문 상태와 이벤트를 별도 프로세스(상주 서비스, 메시지 큐, 데이터베이스)가 관리하고 엔진은 그 서비스에 요청한다.
- **장점**: 엔진이 죽어도 주문 상태 추적이 계속된다. 여러 계좌·장중 거래로 확장하기 쉽다.
- **단점**: 상주 프로세스, 감시, 배포, 저장소 운영 비용이 크다. 하루 1회 점검 운영에서는 이점보다 장애 지점이 늘어난다. 서비스 자체의 장애가 새 불명확 상태를 만든다.

### 5.4 비교

| 기준 | A (SDK 직접) | B (공통 Adapter) | B + 최소 영속 기록 (권장) | C (별도 서비스) |
|---|---|---|---|---|
| 복잡도 | 낮음 | 중간 | 중간 | 높음 |
| 테스트 가능성 | 낮음 (실제 브로커 필요) | 높음 (시뮬레이터) | 높음 | 높음 (서비스까지 띄워야 함) |
| 금융 안전성 | 낮음 (연구 코드에서 주문 가능, R-3 위반) | 높음 | **높음** + 제출 시도 기록과 매 재시작 대조로 불명확 주문을 찾을 수단이 생김 (저장소 보장 수준은 Q12-7) | 높음 |
| 장애 복구 | 낮음 | 프로세스가 죽으면 진행 중 주문 정보를 잃을 수 있음 | **제출 시도 기록(BR-3)과 매 재시작 대조로 복구 시도.** 기록 보존은 저장소가 구현·검증되기 전까지 보장하지 않음 | 높음 (서비스가 상태 유지) |
| 개인 운영 비용 | 낮음 | 낮음 | **낮음** (같은 프로세스 안의 추가 전용 기록) | 높음 |
| ACCEPTED ADR과의 관계 | ADR-0004 R-3 위반 | 부합 | 부합. ADR-0009 §6.1의 Paper/Live 추가 전용 기록을 그대로 활용 | 부합하나 범위 초과 |

## 6. Proposed Decision

### 6.1 결정 요지

**B에 최소 영속 기록을 더한 형태를 채택한다.** 엔진과 코어는 프로젝트가 정한 Adapter 계약(port)만 알고, 브로커별 구현과 Paper 시뮬레이터가 같은 계약을 구현한다. 주문을 보내기 전에 주문 의도를 추가 전용 기록에 먼저 남긴다 (BR-3). 별도 라우팅 서비스(C)는 지금 채택하지 않는다 (Q12-9).

- 계약은 **개념 수준**이다. 함수 시그니처와 자료형은 P0-03에서 정한다.
- 브로커 동작은 모두 UNVERIFIED다. 브로커를 선정하면 기능 선언(§6.3)을 채우고 검증한 뒤에만 Live 여부를 판단한다.
- 이 ADR은 ACCEPTED ADR-0003의 상태·해제 원칙과 ADR-0009의 규칙을 바꾸지 않는다. 그 규칙을 Adapter 경계에 적용한다.

### 6.2 Port 구성 (PLANNED, 이름은 가칭)

| Port | 내용 | 쓰는 모드 |
|---|---|---|
| Broker Query (읽기 전용) | 계좌·포지션·미체결·주문 상태·체결 내역·현금·증거금·세션 조회 | Paper, Live |
| Broker Order (쓰기) | 주문 제출, 취소, 정정 | Paper(시뮬레이터), Live. **실행 경계만 호출** (ADR-0010 PK-11) |
| Market Data | 가격·quote·FX 관측 (ADR-0004, ADR-0007, ADR-0008) | Backtest(파일·fixture), Paper, Live |
| Persistence | 주문 의도·주문·체결·현금 이벤트의 추가 전용 기록 (ADR-0009 §6.1) | Paper, Live (Backtest는 선택) |
| Clock | 현재 시각 제공. 코어는 시각을 조회하지 않고 받기만 한다 | 모든 모드 |

읽기와 쓰기를 나누는 이유: 대조와 복구에는 쓰기 권한이 필요 없다. 읽기 전용 연결만으로 Reconciliation을 할 수 있으면 복구 중 실수로 주문이 나갈 위험이 줄어든다 (CLAUDE.md §8 권한 분리).

### 6.3 기능별 개념 계약

| BF-10 | Replace Order | P, L (선택) | 엔진이 요청. Adapter: 전송·결과 분류 | 기존·새 주문의 식별자, 정정 수량과 그 의미(누적/남은, Q9-10), 브로커 시각 | **Live를 막지 않음.** 미지원이면 정정을 쓰지 않고 "취소 확정 후 새 주문"으로만 바꾼다. 두 주문이 동시에 유효한 상태를 만들지 않는다 | RP-1~RP-5 그대로 (상품 위험 증가 차단, timeout이면 `UNKNOWN` → `HALTED`) |

| BF-12 | Session / Market Status | B, P, L | Backtest: 달력 데이터 (ADR-0007). - Backtest는 BF-1~BF-11을 쓰지 않는다. 체결은 시뮬레이션 정책이고 포지션은 체결 기록에서 계산한다 (ADR-0009 §6.5).
- "Live 금지"는 Live 시작 시 설정 검증 단계에서 거부한다는 뜻이다 (BR-1). Paper(시뮬레이터)에서는 기능을 일부러 빼서 이 검증을 시험할 수 있다.

### 6.3a 조회 결과의 기준 시각 계약 (R1)

BF-1~BF-6의 결과로 대조(ADR-0003 S-3, ADR-0009 R9-8)를 하려면, 여러 조회 결과가 **같은 시점의 완전한 기록**이어야 한다. 브로커가 이를 어떻게 보장하는지는 UNVERIFIED다. 두 경우로 나눈다.

| 구분 | 조건 | 대조 방식 | 설명된 차이 | Live |
|---|---|---|---|---|
| **A. 신뢰할 수 있는 `as_of`** | 브로커가 "이 결과는 `as_of`까지의 모든 이벤트를 반영한 시점 기록"이라고 문서로 정의하고(가능하면 그 시점까지 반영한 이벤트 순번·마지막 체결 ID도 제공), 그 의미를 모의 환경에서 확인함 (BR-1 기능 선언에 `SNAPSHOT_AS_OF` + `VERIFIED_SANDBOX`) | 내부 장부를 같은 `as_of`로 맞춰 비교 (ADR-0009 R9-13, BR-9) | `as_of` 이후의 체결(`fill_at` 또는 이벤트 순번이 `as_of` 뒤)로 정확히 설명되는 차이만 | 다른 Live 필수 기능이 갖춰지면 가능 |
| **B. `as_of` 없음 또는 의미 미보장** | 시각이 없거나, 응답 생성 시각일 뿐이거나, 조회 항목마다 반영 시점이 다를 수 있음 | 아래 대체 검증 (모두 A보다 약함) | **없음.** 모든 차이는 불일치 → `HALTED` | **사용자 승인 대상** (Q12-15). 승인 전에는 B만 제공하는 브로커로 Live를 시작하지 않는다 (BR-1) |

**기능별 요구**: BF-1(계좌)·BF-2(포지션)·BF-6(현금)은 시점 기록 `as_of`, BF-3(미체결)·BF-5(체결 내역)는 그 조회가 어느 이벤트까지 반영했는지 나타내는 상한(이벤트 순번, 마지막 체결 ID 등), BF-4(주문 상태)는 갱신 시각이 필요하다. 대조에 쓰는 조합 가운데 하나라도 갖추지 못하면 그 조합은 B로 본다.

**B에서 쓰지 않는 판단**: "일정 시간 체결 통보가 없고 미체결이 없다"는 것만으로 조회 결과가 완전하고 같은 시점의 기록이라고 단정하지 않는다. 브로커 내부에서 포지션·현금 집계가 체결 기록보다 늦게 갱신될 수 있기 때문이다 (UNVERIFIED).

**B의 대체 검증 후보 (제안)**

| ID | 방법 | 확인하는 것 | 한계 |
|---|---|---|---|
| SB-1 | **앞뒤 경계 읽기**: 체결 내역(또는 이벤트 순번)의 상한 H1을 읽고 → 포지션·현금·미체결을 읽고 → 다시 상한 H2를 읽는다. H1 = H2이고 미체결이 없을 때만 한 묶음으로 본다 | 읽는 동안 새 이벤트가 없었음 | 브로커 내부 집계 지연은 배제하지 못함 |
| SB-2 | **반복 안정성**: SB-1을 간격을 두고 여러 번 반복해 같은 결과가 나오는지 확인 | 일시적 지연 가능성 감소 | 증명이 아님. 횟수·간격은 Q9-4 |
| SB-3 | **체결 내역 재계산**: 검증된 기준 포지션에 브로커 체결 내역(BF-5)을 더한 값, 브로커 포지션(BF-2), 내부 장부를 세 갈래로 비교 | 체결 기록과 포지션 집계의 일관성 | 체결 내역 자체가 늦으면 세 값이 함께 틀릴 수 있음 |
| SB-4 | **브로커 공식 일말 보고서**(결제일 기준 잔고·체결 명세)가 있으면 일간 대조의 기준으로 사용 | 브로커가 확정한 일말 기록 | 제공 여부·지연 UNVERIFIED. 장중 판단에는 쓸 수 없음 |

- B에서 대체 검증이 모두 일치해도 그것은 **약한 일치**다. 약한 일치를 ADR-0003의 "대조 완료"(`HALTED` 해제 조건, S-3)로 인정할지는 사용자 승인 대상이다 (Q12-15). 승인 전에는 인정하지 않는다.
- 어느 경우에도 ADR-0003의 Reconciliation과 `HALTED` 규칙은 완화하지 않는다. 설명되지 않는 차이는 `HALTED`다.

### 6.4 Adapter 규칙 (제안)

| ID | 규칙 | 근거 |
|---|---|---|
| BR-1 | **기능 선언**: 각 Adapter는 §6.3의 기능마다 지원 여부와 확인 수준을 선언한다. 확인 수준 후보: `UNVERIFIED`, `DOCUMENTED`(브로커 문서), `VERIFIED_SANDBOX`(브로커 모의 환경에서 실제 확인). Live 시작 시 "Live 금지" 표시 기능이 하나라도 기준 수준에 못 미치면 **ValueError로 시작을 거부**한다. 기준 수준은 Q12-2. 조회 기능(BF-1~BF-6)은 시각 의미(BR-7)도 함께 선언하며, §6.3a의 A 조건을 갖추지 못한 브로커는 Q12-15에서 대체 검증이 승인되기 전까지 Live 시작을 거부한다 (R1) | ADR-0002 §6.4 fail-closed, ADR-0009 §6.4 |
| BR-2 | **요청 결과 분류**: 쓰기 요청(BF-8~BF-10)의 결과는 `NOT_SENT` / `REJECTED` / `ACKNOWLEDGED` / `UNKNOWN` 가운데 하나이고, `NOT_SENT`에는 원인을 붙인다 (R1). `NOT_SENT(LOCAL_VALIDATION)`: 전송 전에 시스템 자신의 검증(수량 단위, 필수 필드 등)에서 막힘. `NOT_SENT(CONNECTION)`: 연결이 수립되지 않아 주문 요청의 어떤 부분도 나가지 않았음을 Adapter가 **증명할 수 있음**. 어떤 전송 오류가 이를 증명하는지는 브로커·SDK마다 다르다 (UNVERIFIED). 증명할 수 없으면 `UNKNOWN`이다. `REJECTED`는 브로커가 받은 뒤 거부했음을 응답으로 확인한 경우다. 원인별 주문 상태와 Trading State는 §6.5와 AT-0012-12. **응답을 받지 못했다고 해서 주문이 없다고 추정하지 않는다** | ADR-0009 R9-4, ADR-0003 §6.3, §6.5 |
| BR-3 | **제출 시도 기록 (write-ahead, R1)**: 실행 경계는 다음 순서를 지킨다. (0) 로컬 입력 검증은 (1) 전에 한다. 실패하면 제출 시도 이벤트를 만들지 않고 검증 거부 이벤트(사유 코드)만 남긴다 (`NOT_SENT(LOCAL_VALIDATION)`, 주문은 `INTENT`). (1) Client Order ID, 주문 내용, 로컬 시도 시각(가칭 `submit_attempted_at`)을 담은 **제출 시도 이벤트를 만든다** (주문 상태는 `INTENT`). (2) 저장소에 **기록을 요청**한다. (3) 저장소가 **자신이 보장하는 수준의 영속화 성공을 확인**해 줄 때까지 기다린다. 확인을 받지 못하면(실패, 시간 초과, 응답 없음) **주문을 보내지 않는다.** (4) 확인을 받은 뒤에만 전송 절차를 시작한다. **전송 확정 지점**(가칭: 주문 요청의 어떤 부분이라도 브로커 쪽으로 나갈 수 있게 되는 시점. 예: 수립된 연결에 요청을 쓰기 시작하거나 그런 동작을 하는 SDK 호출을 시작하는 시점. 구체 지점은 SDK마다 다르며 UNVERIFIED) **전**의 실패(예: 연결 수립 실패)는 `NOT_SENT(CONNECTION)`이며 주문은 `INTENT`로 남는다. 이 경우 주문은 `PENDING_SUBMIT`을 거치지 않으므로 ACCEPTED ADR-0009 §6.2가 허용하지 않는 "로컬 판단에 의한 상태 되돌림"이 생기지 않는다. 전송 확정 지점을 **넘은 뒤에** `PENDING_SUBMIT`(ADR-0009 §6.2: 제출 요청을 보냈음)과 `order_submitted_at`의 후보 값(로컬 시각. 최종 의미는 Q12-13)을 기록한다. 이 지점을 넘은 뒤의 실패는 `NOT_SENT`를 증명할 수 없으므로 `UNKNOWN`이다. (5) 브로커 응답, 체결 조회 결과, 그리고 `NOT_SENT(원인)` 결과를 모두 이벤트로 기록한다. `NOT_SENT` 결과가 기록된 제출 시도는 재시작 때 "결과가 있는" 시도다. (6) **재시작 시** 기록과 관계없이 먼저 브로커 대조(미체결, 마지막 확인 시점 이후 체결, 포지션, 현금)를 한다. 뒤따르는 결과가 없는 제출 시도(전송 확정 지점을 넘었는지 알 수 없음)와 최종 결과가 없는 `PENDING_SUBMIT` 주문은 `UNKNOWN`으로 보고 계좌를 `HALTED`로 바꾼 뒤 조회한다. **잔여 위험**: 기록을 잃었고 브로커 반영도 늦으면 대조로도 그 주문을 찾지 못할 수 있다 ("찾지 못함"은 부재의 증거가 아님, BR-4). 그래서 비정상 종료 뒤의 재시작은 그런 주문이 보이지 않더라도 대조가 끝나고 사용자가 승인할 때까지 `HALTED`로 시작하는 것을 제안한다 (Q12-16). 저장소 종류, 트랜잭션, 디스크 동기화 방식과 "영속화 성공"의 보장 수준은 Q12-7에서 정한다. **저장소가 구현·검증되지 않은 지금은 충돌이나 전원 장애에서 기록이 반드시 남는다고 보장하지 않는다.** 그래서 (6)의 재시작 대조를 기록 내용과 무관하게 항상 한다. (3)에서 확인을 받지 못한 경우의 계좌 상태는 `HALTED`를 제안한다 (Q12-16). `order_submitted_at`의 정확한 의미는 Q12-13 | ADR-0009 §6.1, §6.2, ADR-0001 §5.1.1, ADR-0003 §6.5 |
| BR-4 | **재시도와 상태 조회의 구분**: `UNKNOWN` 뒤 자동으로 할 수 있는 것은 같은 Client Order ID·Broker Order ID로 하는 **읽기 조회뿐**이다. 같은 주문 의도의 **재제출은 자동으로 하지 않는다.** 조회 결과 "찾지 못함"도 주문이 없다는 증거가 아니다 (브로커 반영 지연 가능). 주문이 없다고 판단하려면 대조(미체결, 제출 시도 이후 체결 내역, 포지션)와 사용자 확인이 필요하다. 수동 재제출을 허용할지와 그 방법은 Kill Switch·복구 설계 문서의 범위다 (ADR-0003 Q3-6, ADR-0009 Q9-8). 이 ADR은 정하지 않는다 (Client Order ID 규칙은 Q12-4) | ADR-0009 R9-5, ADR-0003 §6.5 Kill Switch 제약 |
| BR-5 | **SDK·전송 계층의 자동 재시도 금지**: 쓰기 요청에 대해 SDK나 HTTP 클라이언트가 스스로 재전송하는 기능을 끈다. 브로커가 Client Order ID 중복 방지를 보장한다고 확인된 경우에도 재전송 여부는 엔진이 정하지, 전송 계층이 정하지 않는다 | 중복 주문 방지. SDK 동작은 UNVERIFIED |
| BR-6 | **Adapter는 번역과 결과 분류만 한다.** 금융 계산, 위험 판단, 상태 전이 결정을 하지 않는다. 브로커 상태를 ADR-0009 §6.2 상태로 번역하는 표는 Adapter가 갖되, 번역할 수 없는 상태는 `UNKNOWN`으로 넘긴다 | ADR-0004 R-3, ADR-0010 PK-5 |
| BR-7 | **시각 기록 (R1)**: 모든 응답에 로컬 요청 시각, 로컬 수신 시각, 브로커가 준 시각(있으면)과 **그 시각의 의미**를 함께 기록한다. 의미는 기능 선언(BR-1)에 `SNAPSHOT_AS_OF`(§6.3a의 A) / `RESPONSE_TIME_ONLY` / `NONE` 가운데 하나로 적는다. `SNAPSHOT_AS_OF`가 확인되지 않은 시각은 대조 기준 시각으로 쓰지 않는다 | ADR-0001 §5.1, ADR-0009 R9-13 |
| BR-8 | **재연결**: 연결이 끊기면 `HALTED`다 (브로커 연결 이상). 다시 연결되면 미체결, 내부의 종료되지 않은 모든 주문의 상태, 마지막으로 확인한 이벤트 이후의 체결 내역(겹치는 구간 포함), 포지션, 현금을 다시 읽고 대조한다. 대조가 끝나도 자동으로 `NORMAL`로 돌아가지 않는다 (원인 해소 확인 + 대조 완료 + 사용자 승인) | ADR-0003 §6.5 |
| BR-9 | **포지션·현금 보고 지연 (§6.3a의 A에만 적용)**: 브로커 보고와 내부 장부를 같은 `as_of`로 맞춰 비교한다. `as_of` 이후의 체결로 정확히 설명되는 차이만 설명된 차이로 본다. 설명된 차이가 있는 동안은 대조가 끝나지 않은 것이므로 이 경우 `as_of` 시점의 대조(S-3)는 맞지만 현재 보유가 브로커 기준으로 아직 확인되지 않았으므로 위험 축소 자동 주문은 S-1 미확인(`POSITION_UNCONFIRMED`)으로 차단하고, 위험 증가 자동 주문은 다음 일치 확인까지 보류한다 (제안). 그 밖의 차이는 불일치 → `HALTED`. 현금의 허용 오차는 ADR-0003 Q3-12 | ADR-0003 S-3, ADR-0009 R9-8 |
| BR-10 | **기준 시각이 없거나 의미가 보장되지 않는 브로커 (§6.3a의 B, R1)**: 설명된 차이를 인정하지 않는다. 모든 차이는 불일치 → `HALTED`. "정지 상태"(미체결 없음, 일정 시간 체결 통보 없음)는 대조를 시작하는 **전제 조건**일 뿐 완전성의 증거가 아니다. 대체 검증 SB-1~SB-4로 얻은 일치는 약한 일치이며, 이를 대조 완료로 인정할지와 B만 제공하는 브로커의 Live 허용 여부는 사용자 승인 대상이다 (Q12-15) | ADR-0003 §6.5, S-3 |
| BR-11 | **데이터 정정**: 브로커가 과거 체결을 정정·취소하면 명시적 정정 이벤트로만 반영한다 (Q9-11). 다시 읽은 내역이 이전과 예고 없이 다르면 무결성 오류 → `HALTED` | ADR-0009 §6.4a |
| BR-12 | **취소 확정과 체결 통보의 순서 불일치**: 취소 확정이 보고한 누적 체결 수량과 내부 체결 기록의 합이 다르면 ACCEPTED ADR-0009 RP-4를 그대로 적용한다. 그 주문은 `UNKNOWN`, 계좌는 `HALTED`다. 최악 경우 노출은 ACCEPTED ADR-0003 §6.3과 ADR-0009 §6.2(`UNKNOWN`은 전량 체결된 것으로 간주), R9-7에 따라 **원래 주문 수량 전체**로 본다 (확인된 체결 + 확인되지 않은 남은 수량). 브로커 취소 확정의 누적 수량으로 최악 경우를 줄이지 않는다. 줄일 수 있는 조건은 Q12-14 (R1). 늦은 체결 통보가 와서 수량이 맞아도 자동으로 해제하지 않는다 (원인 해소 확인 + 대조 완료 + 사용자 승인). 일정 시간 기다린 뒤에 `HALTED`로 바꾸는 완화는 RP-4를 바꾸는 일이므로 이 ADR에서 제안하지 않는다 (Q12-12) | ADR-0009 R9-6, RP-4, R9-8 |
| BR-13 | **NAV를 확정할 수 없을 때**: 순자산이 0이 아닌 통화의 평가 환율이 없으면 NAV를 확정하지 않는다 (ADR-0008 §6.5). 이때 계좌 단위 지표(gross leverage, 증거금 사용률)를 계산할 수 없으므로 **모든 상품의 위험 증가 주문을 막는다** (제안). ADR-0008 §6.5가 정한 최소 범위(그 통화 상품의 위험 증가 차단)보다 넓다. Trading State를 바꿀지는 ADR-0002 Q2-8, ADR-0003 Q3-13 | ADR-0003 §6.2.2 fail-closed 원칙의 확장 (Q12-10) |
| BR-14 | **자격증명**: `app`이 저장소 밖에서 읽어 Adapter에 넘긴다. 코드·테스트·로그·문서·커밋·기록에 남기지 않는다. 기록에는 계좌 ID의 비식별 표시만 남기는 것을 검토한다 (Q12-11) | CLAUDE.md §5, §8 |
| BR-15 | **수수료 통화**: Adapter는 브로커가 보고한 수수료 금액과 통화를 원본 그대로 기록한다. 그 통화를 운영 회계에 쓸지는 ACCEPTED ADR-0008의 미결정 사항이다 (F8-3, Q8-11, ADR-0001 Q1-4) | ADR-0008 §6.10 |
| BR-16 | **조회 실패의 범위**: 연결이 끊기거나 BF-1~BF-6, BF-11 조회가 실패하면 S-1~S-3을 확인할 수 없으므로 브로커 연결 이상으로 보고 `HALTED`다. 연결은 정상이고 BF-7(증거금)이나 BF-12(세션) 조회만 실패하면 계좌 상태를 바꾸지 않고, 그 판단에 의존하는 동작만 막는다 (BF-7: 위험 증가 차단, BF-12: 그 시장에 제출하지 않음) | ADR-0003 §6.5, §6.2.1, §6.2.2 |

### 6.6 멱등성과 식별자

| 식별자 | 만드는 쪽 | 역할 | 범위·주의 |
|---|---|---|---|
| Client Order ID | 시스템 | 주문 의도 하나의 고유 키. 제출 전 기록(BR-3), 상태 조회, 중복 제출 방지 | 다른 의도에 다시 쓰지 않는다. 비밀정보를 담지 않는다. 길이·문자 제한과 브로커가 중복 방지 키로 인정하는지는 UNVERIFIED (Q9-1) |
| Broker Order ID | 브로커 | 브로커 측 조회·취소 | 접수 응답 전에는 없다. 없는 채로 timeout이면 Client Order ID 조회(BF-11)만이 수단이다 |
| Fill ID | 브로커 (Paper는 시뮬레이터) | 체결 반영의 멱등 키 (ADR-0009 §6.4a) | 고유성 범위는 UNVERIFIED (Q9-11). 없거나 범위가 좁으면 아래 대안 표 |
| Account ID | 브로커 | 모든 키의 범위 | 다른 계좌의 ID와 섞이지 않게 모든 키에 포함 |
| Order Group ID | 시스템 | 롤 다리 묶음 (ADR-0009 R9-10) | 브로커의 묶음 주문 기능을 가정하지 않는다 |
| Broker Event ID | 브로커 (있으면) | 이벤트 스트림의 중복 제거와 누락(순번 공백) 검출, 재연결 후 이어 받기 | Fill ID와 다르다. 순번 보장 여부는 UNVERIFIED |

**같은 요청의 재시도와 상태 조회**: 재시도(같은 쓰기 요청을 다시 보냄)는 주문을 하나 더 만들 수 있다. 상태 조회(읽기)는 주문을 만들지 않는다. `UNKNOWN`에서는 상태 조회만 자동으로 한다 (BR-4). 브로커가 Client Order ID 중복 방지를 **보장한다고 확인되더라도** 자동 재제출을 허용하는 것은 ACCEPTED ADR-0009 R9-5를 바꾸는 일이므로 이 ADR에서 제안하지 않는다.

**체결 ID가 없거나 고유하지 않은 브로커의 대안 (비교)**

| 대안 | 내용 | 위험 | 판단 |
|---|---|---|---|
| (a) 자연 복합 키 | (계좌, Broker Order ID, `fill_at`, 수량, 가격)을 키로 | 같은 초·같은 가격의 부분 체결 두 개가 하나로 합쳐짐 → **체결 과소 반영**. 필드 표현이 조금만 달라도 하나가 둘로 나뉨 → 과대 반영 | 단독으로는 Live에 쓰지 않는다 |
| (b) 누적 수량 대조 | 주문별 브로커 누적 체결 수량의 증가분으로 체결을 만든다 | 중복·순서에 강하다. 체결별 가격·수수료가 평균값으로 뭉개질 수 있다 → 체결분 손익·수수료 회계의 정밀도 저하 (ADR-0001 체결분 항) | (c)의 교차 검증으로 권장 |
| (c) 이벤트 순번 | 브로커 이벤트 순번으로 중복 제거와 누락 검출 | 순번이 공백 없이 순서대로라는 보장이 필요 (UNVERIFIED) | 보장이 확인되면 사용 가능 |
| (d) Live 부적합 판정 | 체결 중복 제거를 신뢰할 수 없으면 그 브로커는 Paper까지만 | 운영 선택지가 줄어듦 | 안전한 기본 |

권장 (Q12-3): Live에는 (1) 고유성 범위가 확인된 체결 ID, 또는 (2) 보장이 확인된 이벤트 순번(c)과 누적 수량 대조(b)의 조합이 있어야 한다. (a) 단독은 허용하지 않는다. 둘 다 없으면 (d)다. 고유한 식별자를 만들 수 없어 중복 제거를 신뢰할 수 없다면 Live 가능 여부를 **별도로 판단**하고 사용자 승인을 받는다.

### 6.7 Paper 시뮬레이터와의 관계

- Paper 시뮬레이터(PLANNED)는 Broker Query·Broker Order port를 **같은 계약으로** 구현한다. 엔진은 상대가 시뮬레이터인지 브로커인지 모른다.
- 체결가 계산은 `app`이 `lab.accounting`의 순수 함수를 주입한다 (ADR-0010 PK-5). 시뮬레이터가 코어를 직접 import하지 않는다.
- 시뮬레이터는 **실패 주입 각본**을 받는다. 같은 각본과 같은 시드는 같은 이벤트 순서를 만든다. 시드와 각본 ID는 실행 manifest에 기록한다 (ADR-0011 `lab-run`).
- 기능 선언(BR-1)도 각본으로 바꿀 수 있어야 한다. 예: "Client Order ID 조회 없음"으로 실행해 Live 시작 거부를 시험한다.
- 재현해야 하는 상황: 즉시 전량 체결, 부분 체결, 주문 거부, 제출 timeout(접수됨 / 접수 안 됨), 늦은 체결 통보, 중복 체결 통보, 같은 체결 ID의 다른 내용, `CANCEL_REQUESTED` 상태의 지연과 그 사이 체결, `REPLACE_REQUESTED` 상태의 지연(원자적 / 비원자적), `UNKNOWN`, 조회 실패, 연결 끊김과 재연결, 포지션·현금 보고 지연, 기준 시각이 없는 조회 결과(§6.3a의 B), 저장소의 영속화 확인 실패(BR-3 (3)), Reconciliation 불일치.
- 시뮬레이터는 실제 시장의 유동성이나 체결 확률을 재현한다고 주장하지 않는다. 실패 처리 경로를 시험하는 도구다. 부분 체결·거부를 백테스트 성과 시뮬레이션에 넣을지는 ADR-0009 Q9-7이다.

### 6.8 Kill Switch와 Adapter의 경계

| 구분 | 내용 | 브로커 통신 | 근거 |
|---|---|---|---|
| 신규 위험 증가 차단 | 상품 단위는 ADR-0002 신호 적격성과 L2 정책 결정이, 계좌 `RESTRICTED`는 L3 상태 게이트가 위험 증가 주문을 거부 | 불필요 (내부 판단) | ADR-0002, ADR-0003 §6.1, §6.5 |
| `RESTRICTED`의 검증된 위험 축소 | S-1~S-7과 §6.2.2를 모두 통과한 축소만 허용. S-1~S-3에 BF-2, BF-3, BF-6 조회가 필요하다. 조회할 수 없으면 축소도 차단 | 읽기 조회 필요 | ADR-0003 §6.2.1 |
| `HALTED`의 자동 주문 금지 | 위험 축소 포함 자동 주문 없음. 상태 전이(Kill Switch (1))는 내부 동작이라 브로커가 응답하지 않아도 즉시 된다 | 불필요 | ADR-0003 §6.5 |
| 수동 복구와 재승인 | 별도 설계 문서 (ADR-0003 Kill Switch (2), Q3-6, ADR-0009 Q9-8, CLAUDE.md §8). Adapter는 읽기 조회와 사용자가 명시적으로 실행한 명령만 제공한다 | 필요 | 이 ADR은 절차를 정하지 않음 |

- **취소·조회 API가 있다고 가정하지 않는다.** BF-9(취소)가 없는 브로커에서는 복구가 브로커 화면에서의 수동 조치와 그 뒤의 대조가 된다. 복구 설계 문서는 이 경우를 다뤄야 한다.
- **자동 취소를 기본 동작으로 넣지 않는다.** 일괄 취소는 ACCEPTED ADR-0003이 기본 동작에서 제외했다.
- **취소 성공을 임의로 확정하지 않는다.** 취소 요청의 응답은 `CANCEL_REQUESTED`일 뿐이고, `CANCELLED`는 브로커 확정(누적 체결 수량 포함)을 받은 뒤에만 쓴다 (R9-6).
- ADR-0003의 상태 정의와 해제 원칙은 바꾸지 않는다.

### 6.9 ACCEPTED ADR과의 정합성

| ACCEPTED 결정 | 이 ADR의 대응 | 충돌 여부 |
|---|---|---|

## 7. Consequences / Trade-offs

**장점**
- 브로커가 정해지기 전에 실패 처리 경로를 설계하고 시뮬레이터로 시험할 수 있다.
- 실주문 호출 위치와 브로커 SDK 위치가 한정된다.
- 제출 시도 기록(BR-3)과 매 재시작의 브로커 대조로, 프로세스가 죽은 뒤 불명확 주문을 찾을 수단이 생긴다. 기록이 장애에서 반드시 남는다는 보장은 저장소 결정(Q12-7)과 검증 이후의 일이다.

**단점과 비용**
- 보수적 규칙 때문에 `HALTED`가 자주 생길 수 있다. 연결이 잠깐 끊겨도 사용자 승인이 필요하다 (Q3-5, Q12-5). 하루 1회 점검 운영에서는 다음 점검까지 거래가 멈출 수 있다.
- 기능 선언과 확인 수준을 브로커마다 관리해야 한다.
- 정정과 취소가 제한된 브로커에서는 주문 관리가 단순해지는 대신 체결 기회를 잃을 수 있다.

## 8. Compatibility with V1

이 ADR은 ADR-0001 §8.0(세 ADR 공통)의 `V1_COMPAT` 적용 범위를 그대로 따른다.

| 항목 | 영향 |
|---|---|
| V1 코드와 306개 테스트 | 영향 없음. V1에는 브로커 경로가 없다 |
| V1 API | Paper/Live 주문 경로에서 호출하지 않는다 (ADR-0001 §8.0) |
| `execute_market_order` | 백테스트 체결 시뮬레이션으로 남는다. Paper 시뮬레이터의 체결가 계산에 재사용할지는 ADR-0010 Q10-2 |

## 9. Financial Integrity Implications

- **중복 주문**: 응답 유실을 "주문 없음"으로 보고 재제출하면 의도한 노출의 두 배가 된다. BR-2~BR-5가 막는다.
- **체결 이중 반영과 누락**: 체결 ID가 없거나 범위가 좁으면 포지션과 현금이 틀어진다. §6.6의 대안 (a)는 같은 초·같은 가격 부분 체결에서 과소 반영을 만든다.
- **정정 중 과소 평가**: 비원자적 정정에서 max 규칙은 노출을 과소 평가한다 (ADR-0009 CE-1). BF-10은 RP-1~RP-5를 그대로 쓴다.
- **보고 지연을 불일치로 오인 / 불일치를 지연으로 오인**: 기준 시각 없이 비교하면 둘 다 생긴다. BR-9, BR-10.
- **NAV 미확정 상태의 주문**: 환율이 없을 때 계좌 단위 지표 없이 위험 증가 주문을 내면 한도 검사가 무력해진다. BR-13.
- **수수료 통화**: 브로커 보고 통화를 운영 회계에 바로 쓰는 것은 ACCEPTED ADR-0001의 잠정 가정을 바꾸는 일이다. BR-15는 기록만 한다.

## 10. Acceptance Criteria

인수 테스트는 **명세**다. 이번 작업에서 구현하지 않았다. 모든 시나리오는 Paper 시뮬레이터(실패 주입)로 실행할 수 있어야 한다 (AT-0012-10). 상품은 가상의 선물 월물 `F1-A`, 가격과 식별자는 기록 형식을 보이기 위한 값이다. 최악 경우 노출은 ADR-0003 §6.3의 수량 기준이다.

각 테스트의 기대 결과: **주문 상태 / 실제 포지션 / Trading State / 자동 주문 허용 / 사용자 개입**.

### AT-0012-1 제출 timeout 후 실제로는 주문이 접수되어 있었음

- **입력**: 실제 포지션 0. 주문 의도 `C-101` 매수 +5. BR-3에 따라 제출 시도 이벤트를 기록하고 저장소의 영속화 확인을 받은 뒤 전송을 시작하며 `PENDING_SUBMIT` 기록. 응답 없이 timeout. 이후 Client Order ID 조회 결과: Broker Order ID `B-77`, `ACCEPTED`, 체결 0. 그 뒤 체결 통보 `X-501` +5 @ 100.00.
- **기대 결과**:

| 시점 | 주문 상태 | 실제 포지션 | 최악 경우 롱 | Trading State | 자동 주문 | 사용자 개입 |
|---|---|---|---|---|---|---|
| timeout 직후 | `UNKNOWN` | 0 | 0 + 5 = **5** | `HALTED` | 금지. 상태 조회만 | 필요 |
| 조회 후 | `ACCEPTED` (`B-77`) | 0 | 5 | `HALTED` 유지 | 금지 | 필요 |
| 체결 통보 후 | `FILLED` | **+5** (한 번 반영) | 5 | `HALTED` 유지 | 금지 | 원인 확인 + 대조 + 승인 후 해제 |

- **금지**: timeout 직후 `C-101`이나 새 ID로 다시 제출하는 것 (R9-5, BR-4).
- **새 테스트 후보**: `test_submit_timeout_then_found_accepted_is_not_resubmitted`

### AT-0012-2 Client Order ID로 상태를 조회할 수 없음

- **입력**: (a) Adapter 기능 선언에서 BF-11의 Client Order ID 조회가 없고, BF-3·BF-5 응답도 Client Order ID를 돌려주지 않음. Live 시작 시도. (b) 같은 선언으로 Paper 실행 중, Broker Order ID를 받기 전에 timeout.
- **기대 결과**:
  - (a) 설정 검증 단계에서 **ValueError**. Live가 시작되지 않는다 (BR-1). 주문 0건. 시작 전이므로 Trading State와 자동 주문은 해당 없음. 사용자는 브로커나 설정을 바꿔야 한다.
  - (b) 주문 `UNKNOWN`, 계좌 `HALTED`, 자동 주문 금지. 시스템은 주문을 식별할 수 없으므로 사용자가 브로커 측에서 확인해야 한다. 미체결 목록에 비슷한 주문이 있어도 속성이 비슷하다는 것만으로 같은 주문이라고 단정하지 않는다.
- **새 테스트 후보**: `test_live_start_rejected_without_client_order_lookup`, `test_unidentifiable_timeout_order_halts`

### AT-0012-3 같은 체결을 두 번 수신

- **입력**: 주문 `C-201` +5 `ACCEPTED`. 체결 `X-1` +2 @ 100.25, 수수료 4.00 USD, `fill_at` 10:00:01Z. 같은 내용이 두 번 도착 (ADR-0009 AT-0009-4와 같은 성질).
- **기대 결과**: 실제 포지션 **+2** (한 번만), 남은 수량 3, 주문 `PARTIALLY_FILLED`, Trading State 그대로(`NORMAL`), 자동 주문은 정상 검사를 거쳐 허용, 사용자 개입 불필요. 두 번째 수신은 중복 기록만 남긴다.
- **새 테스트 후보**: `test_duplicate_fill_notification_applied_once`

### AT-0012-4 같은 체결 ID인데 내용이 다름

- **입력**: AT-0012-3 뒤에 `X-1`이 `fill_at` 10:00:02Z로 다시 도착 (다른 필드는 같음).
- **기대 결과**: 무결성 오류. 두 번째 기록은 반영하지 않고 두 기록을 모두 보관. 실제 포지션 **+2** 유지, Trading State **`HALTED`**, 자동 주문 금지, 사용자 개입 필요 (ADR-0009 AT-0009-10).
- **새 테스트 후보**: `test_conflicting_fill_with_same_id_halts`

### AT-0012-5 취소 응답보다 체결 통보가 늦게 도착

- **입력**: 주문 `C-301` +5. 체결 `X-11` +2 반영(포지션 +2). 취소 요청 → `CANCEL_REQUESTED`. 브로커 취소 확정: 누적 체결 3, 취소 2. 그 뒤에 체결 통보 `X-12` +1 도착.
- **기대 결과**:

| 시점 | 주문 상태 | 내부 체결 합 | 브로커 누적 | 최악 경우 롱 | 상품 위험 증가 | Trading State | 사용자 개입 |
|---|---|---|---|---|---|---|---|
| 취소 요청 중 | `CANCEL_REQUESTED` | 2 | — | 2 + 3 = **5** (R9-6) | 정상 검사 | 그대로 | 불필요 |
| 취소 확정 수신, `X-12` 전 | `UNKNOWN` (확정 누적 3 ≠ 내부 2, RP-4) | 2 | 3 | 2 + (5 − 2) = **5** (전량 체결 간주, ADR-0003 §6.3, BR-12) | 금지 | **`HALTED`** | 필요 |
| `X-12` 수신, 상태 조회 전 | `UNKNOWN` 유지 (R9-4: 상태 조회나 체결 통보로 상태가 **확인**될 때까지. 체결 한 건으로는 종료 여부를 확인할 수 없음) | 3 | 3 | 3 + (5 − 3) = **5** | 금지 | `HALTED` 유지 | 필요 |
| 상태 조회로 `CANCELLED`·누적 체결 3을 확인하고 포지션 대조도 일치 | `CANCELLED` (체결 3, 종료) | 3 | 3 | **3** (종료 주문은 남은 수량 없음) | 금지 | `HALTED` 유지 (자동 해제 없음) | 원인 확인 + 대조 완료 + 사용자 승인 |

- 최종 실제 포지션은 **+3**이다. 취소 확정만 보고 +2로 끝내지 않는다.
- **수량 구분 (R1)**: 불일치 시점에 (1) 확정된 체결 = 내부 체결 기록 2, (2) 보고된 누적 체결 = 브로커 취소 확정의 3, (3) 아직 확인되지 않은 체결 가능 수량 = 원래 주문 5 − 확정 2 = 3, (4) ACCEPTED 규칙의 최악 경우 롱 = (1) + (3) = **5**, (5) 대조 완료 전 자동 주문 = **금지**(위험 축소 포함, `HALTED`). 초안의 max(2, 3) = 3은 불일치의 원인인 브로커 보고를 믿고 최악 경우를 줄인 값이라 ACCEPTED ADR-0003 §6.3과 맞지 않아 R1에서 고쳤다. 브로커의 최종 취소 확정 수량을 근거로 상한을 줄일 조건은 Q12-14로 남긴다.
- **새 테스트 후보**: `test_late_fill_after_cancel_confirmation_is_applied`, `test_cancel_fill_mismatch_halts_immediately`, `test_unknown_after_cancel_mismatch_counts_full_original_quantity`

### AT-0012-6 정정 중 기존·신규 주문이 모두 유효할 가능성

- **입력**: ADR-0009 AT-0009-9와 같다. 실제 포지션 0, `C-009` +5 `ACCEPTED`, +8로 정정 요청, 브로커 정정 원자성과 수량 의미는 UNVERIFIED (BF-10 기능 선언: `UNVERIFIED`).
- **기대 결과**: 최악 경우 롱 **5 + 8 = 13** (RP-1). max 규칙의 8을 쓰지 않는다. 그 상품 위험 증가 차단 (RP-3). Trading State 그대로. 정정 응답이 timeout이면 기존·새 주문 모두 `UNKNOWN`, `HALTED`, 재정정·재제출 없음 (RP-5). 이때 최악 경우 롱은 두 주문 모두 전량 체결로 보아 여전히 **13**이다 (ADR-0003 §6.3). timeout이면 사용자 개입 필요.
- **변형**: 기능 선언에서 정정 미지원 → 시스템은 정정 요청을 보내지 않고 "취소 확정 후 새 주문"으로만 바꾼다. 취소 확정 전에는 새 주문을 내지 않는다.
- **새 테스트 후보**: `test_unverified_replace_uses_sum_worst_case`, `test_replace_unsupported_uses_cancel_then_new_sequentially`

### AT-0012-7 브로커 포지션과 내부 포지션 불일치

- **입력**: 같은 기준 시각에서 내부 실제 포지션 +3, 브로커 보고 +2. 미체결 없음. 브로커가 기준 시각을 제공 (ADR-0003 AT-0003-8, ADR-0009 AT-0009-5와 같은 성질).
- **기대 결과**: 대조 불일치 → **`HALTED`**. 위험 축소를 포함한 자동 주문 금지 (S-3). 화면에는 두 값과 차이를 보여 준다. 해제는 원인 확인 + 대조 완료 + 사용자 승인.
- **변형**: 브로커 보고의 기준 시각이 내부 마지막 체결 `fill_at`보다 앞서고, 그 체결이 차이 1과 정확히 맞으면 설명된 차이로 보고 다음 보고를 기다린다 (BR-9). 브로커가 기준 시각을 주지 않거나 그 의미가 확인되지 않으면(§6.3a의 B) 설명된 차이로 보지 않고 `HALTED`다 (AT-0012-11).
- **새 테스트 후보**: `test_position_mismatch_halts`, `test_report_lag_explained_only_with_broker_as_of`

### AT-0012-8 FX 또는 현금 잔액 조회 실패

- **입력**: (a) 브로커 현금 잔액 조회(BF-6)가 실패. (b) 데이터 공급자에서 USD 평가 환율이 없음. 계좌에 USD 순자산이 있음. 브로커 조회는 정상.
- **기대 결과**:

### AT-0012-9 복구 후 중복 주문 없이 다시 실행

- **입력**: 목표 +5, 실제 0. 실행 경계가 `C-401` +5의 제출 시도 이벤트를 기록하고 **저장소의 영속화 확인을 받은 뒤** 전송을 시작한 직후, 결과를 기록하기 전에 프로세스가 죽음. 재시작. 브로커 측에서는 `C-401`이 체결됨 (`X-21` +5 @ 101.00). 저장소가 영속화 확인 후의 기록을 보존했다고 가정한다 (보장 수준은 Q12-7, 지금은 보장하지 않음).
- **기대 결과**:
  1. 재시작 시 먼저 브로커 대조를 시작하고(BR-3 (6)), 기록에서 뒤따르는 결과가 없는 제출 시도 이벤트를 찾는다 → `UNKNOWN`, **`HALTED`**, 최악 경우 롱 0 + 5 = **5**.
  2. `C-401`로 조회 → `FILLED`. 체결 내역에서 `X-21`을 한 번 반영 → 실제 포지션 **+5**.
  3. 대조: 브로커 +5 = 내부 +5. 원인 확인 + 대조 완료 + 사용자 승인 → `NORMAL`.
  4. 다음 의사결정: 새 주문 의도 = 목표 5 − 기대 예상 포지션 (5 + 미체결 0) = **0**. 중복 주문 없음.
- **변형**: 조회 결과 "찾지 못함". 주문이 없다는 증거가 아니다. 기다린 뒤(Q9-4) 미체결과 제출 시도 시각 이후 체결 내역을 다시 확인한다. 그래도 없으면 사용자가 확인한다. **자동 재제출은 하지 않는다** (BR-4). 수동 재제출을 할지와 방법은 복구 설계 문서의 범위다 (ADR-0003 Q3-6, ADR-0009 Q9-8).
- **변형 2 (R1)**: 저장소가 영속화 확인을 주지 않은 상태(실패·시간 초과)에서 프로세스가 죽음. BR-3 (3)에 따라 전송은 시작되지 않았어야 한다. 재시작 시 기록에 제출 시도 이벤트가 남아 있으면(기록은 됐지만 확인만 못 받은 경우) 결과 없는 이벤트이므로 `UNKNOWN`·`HALTED`(최악 경우 롱 **5**)로 보수적으로 처리하고 조회한다. 기록이 없으면 그 의도는 없었던 것으로 보되, 재시작 대조(BR-3 (6))는 그대로 한다.
- **변형 3 (R1)**: 저장소가 영속화 성공을 확인했지만 장애로 기록을 잃음 (현재 보장하지 않는 상황). 기록만으로는 `C-401`을 알 수 없다. 재시작 대조에서 브로커에 내부 기록에 없는 주문·체결(`C-401`, `X-21`)이 보이면 대조 불일치 → **`HALTED`**, 사용자 개입. 이 경우를 잡는 장치는 기록이 아니라 **매 재시작의 브로커 대조**다.
- **새 테스트 후보**: `test_restart_with_pending_submit_recovers_without_duplicate`, `test_not_found_after_timeout_is_not_proof_of_absence`, `test_submit_blocked_without_persistence_ack`, `test_restart_reconciliation_detects_order_missing_from_log`
